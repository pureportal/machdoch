# Host integration patterns for agent CLIs and shared protocols (state as of 2026-10-29)

Scope: (a) cross-agent protocols, mainly the Agent Client Protocol (ACP); (b) how established hosts (Zed, JetBrains Air, VS Code, the Codex app-server consumers, Claude Code surfaces, Conductor, Nimbalyst/Crystal, Sculptor, Claude Squad, Warp, OpenHands) build advanced UX on top of agent CLIs; (c) follow-up suggestions, background agents, and security patterns machdoch could reuse. Many products here ship weekly, so check the version and date given next to each claim. "Secondary" marks third-party write-ups or search-result summaries I couldn't check against a primary page.

## Q1. Agent Client Protocol (ACP): scope, agent support, maturity, gaps vs vendor-native protocols, and whether one integration covers Claude Code, Codex and Copilot CLI

### Takeaway
ACP v1 is stable and actively developed. It is JSON-RPC 2.0 over stdio with capability-gated features, and between Feb and Sep 2026 it stabilized session list, resume, close, delete, config options, usage updates (context and cost), elicitation, request cancellation, and message IDs. All three target CLIs can be reached over ACP: Claude through the `claude-agent-acp` adapter (on the Claude Agent SDK), Codex through `codex-acp` (on the Codex app-server), and Copilot CLI natively with `copilot --acp` (public preview). One integration therefore covers the common baseline: sessions, prompt turns, cancel, permissions, tool calls, plans, diffs, slash commands, modes/models, and MCP passthrough. It does not give full parity. Rate limits, prompt suggestions, goals, review, background-task control and steering are missing from the stable spec, or exist only as vendor- or JetBrains-specific extensions (`_session/steering`, AIR `_meta` extensions). ACP v2 has been in Draft since 2026-07-20.

### Cited Findings
**Spec scope (v1)**
- The transport is JSON-RPC 2.0 (methods plus notifications). Baseline agent methods are `initialize`, `authenticate`, `session/new` and `session/prompt`. Optional, capability-gated methods are `session/load` (`loadSession` capability), `logout` and `session/set_mode`. `session/cancel` is a notification. — [ACP overview](https://agentclientprotocol.com/protocol/overview)
- Client-side methods: `session/request_permission` (baseline); optional `fs/read_text_file`, `fs/write_text_file`, `terminal/create|output|release|wait_for_exit|kill` and `elicitation/create`. The `session/update` notification variants are message/thought chunks, tool calls and tool-call updates, plans, available commands (slash commands), mode changes, user-facing notices, and context compactions. — [ACP overview](https://agentclientprotocol.com/protocol/overview)
- Extensibility: `_meta` fields, underscore-prefixed custom methods, and custom capabilities advertised at initialize. — [ACP overview](https://agentclientprotocol.com/protocol/overview)
- The doc index lists v1 pages for Session List, Session Delete, Session Config Options, Slash Commands, Agent Plan, Terminals, Elicitation, Cancellation and Transports. Its RFDs include session fork, proxy chains ("Agent Extensions via ACP Proxies"), MCP-over-ACP, subagent sessions, session status, session archive, client-set titles, client-provided system prompt, end-turn token usage, plan operations, and Streamable HTTP & WebSocket transport. — [ACP llms.txt index](https://agentclientprotocol.com/llms.txt)

**Stabilization timeline (from the ACP updates page)** — [ACP Updates](https://agentclientprotocol.com/updates)
- 2025-10-24: `clientInfo`/`agentInfo` implementation info.
- 2026-02-04: Session Config Options stabilized (models, modes, reasoning levels). Sergey Ignatov of JetBrains joined as Lead Maintainer, reflecting Zed and JetBrains co-stewardship.
- 2026-02-18: `session/list` stabilized.
- 2026-03-09: ACP Registry released; `session_info_update` (e.g., titles) stabilized.
- 2026-04-22: `session/resume` stabilized (reconnects without replaying history; proxies can build `session/load` on top). A Transports Working Group was formed (WebSocket/HTTP, Draft RFD).
- 2026-04-23: `session/close` stabilized (cancels in-flight work and frees resources without killing the process).
- 2026-05-21: `logout`. 2026-06-01: `session/delete` and `additionalDirectories` (extra workspace roots).
- 2026-06-05: `usage_update` stabilized ("context-window use and optional cumulative cost"); `messageId` stabilized.
- 2026-06-24: `model_config` category. 2026-06-25: Rust and TypeScript SDKs 1.0.0. 2026-06-29: `$/cancel_request`. 2026-07-06: boolean config options. 2026-07-20: **ACP v2 available in Draft**. 2026-07-22: Elicitation stabilized. 2026-09-17: Tool Call Names stabilized.
- `session/resume` is advertised via `sessionCapabilities.resume`. `session/load` replays the full conversation via `session/update`. — [Session Resume stabilized](https://agentclientprotocol.com/announcements/session-resume-stabilized)
- A v2 RFD proposes removing `session/load` and folding optional history replay into `session/resume`. — [v2 Required Session Methods RFD](https://agentclientprotocol.com/rfds/v2/required-session-methods) (from search snippet)

**ACP v2 (Draft)**
- v2 baseline agent methods: `initialize`, `auth/login`, `auth/logout`, `session/new`, `session/prompt`, `session/list`, `session/resume`, `session/close`. Optional: `session/set_config_option` and `session/delete`. Either side may send `$/cancel_request`. — [ACP v2 overview](https://agentclientprotocol.com/protocol/v2/overview)
- v2 prompt lifecycle: the `session/prompt` response returns once the prompt is *inserted* (with `messageId`), not when the work finishes. `state_update` reports `running`, `requires_action` or `idle`. Idle carries a stop reason (`end_turn`, `max_tokens`, `max_turn_requests`, `refusal`, `cancelled`, `error`). "Background activity may continue" while idle, and background completions "do not by themselves start foreground work." — [ACP v2 Prompt Lifecycle](https://agentclientprotocol.com/protocol/v2/prompt-lifecycle.md)
- v2 queueing and steering are explicitly **not** specified: "This does not require Agents to support prompts while work is active". Clients should wait for `idle`. — [ACP v2 Prompt Lifecycle](https://agentclientprotocol.com/protocol/v2/prompt-lifecycle.md)
- v2 cancel semantics: the client marks unfinished tool calls `cancelled` and **must answer pending permission requests with `cancelled`**. The agent then sends idle/`cancelled`. — [ACP v2 Prompt Lifecycle](https://agentclientprotocol.com/protocol/v2/prompt-lifecycle.md)
- `usage_update` has `used` and `size` (tokens, required) and optional `cost` {`amount`, ISO-4217 `currency`}. Compaction is a `compaction_update` entity (`in_progress|completed|failed|cancelled`) with an optional summary. Notices have a severity (`info|warning|error`) plus a title, and are not replayed. — [ACP v2 Prompt Lifecycle](https://agentclientprotocol.com/protocol/v2/prompt-lifecycle.md)

**Agent support**
- The ACP agents page lists 48 agents. Adapters: Claude Agent via `claude-agent-acp`, Codex CLI via `codex-acp`, Pi via `pi-acp`. GitHub Copilot is marked "public preview". Gemini CLI, Cursor, Cline, Goose, OpenCode, OpenHands, Junie, Kiro CLI, Qwen Code, Mistral Vibe, Factory Droid, Augment, Kimi CLI and others are listed without adapter notes. — [ACP Agents](https://agentclientprotocol.com/overview/agents)
- **claude-agent-acp** (`@agentclientprotocol/claude-agent-acp`, Apache-2.0, "Use Claude Agent SDK from any ACP client") supports @-mentions, images, tool calls with permission requests, following, edit review, TODO lists, interactive **and background terminals**, custom slash commands, client MCP servers plus `/mcp` control, nested subagent transcripts / subagent sessions, and an "Ultracode" config option. — [claude-agent-acp](https://github.com/agentclientprotocol/claude-agent-acp)
- claude-agent-acp ships experimental ACP v2 (`CLAUDE_AGENT_ACP_PROTOCOL=v1|v2|auto`). Its v2 baseline includes `session/list`, `session/resume` (with replay), `session/close`, `session/delete` and `session/fork`. "Steering and the AIR extensions are v1 only for now." "Background commands keep running after a cancel either way." Background subagent children keep running after a parent cancel unless the client stops them; children can be cancelled by session id via `Query.stopTask`. Claude Code refuses `/mcp reconnect|enable|disable` in SDK mode, so the adapter uses the SDK control API instead. — [claude-agent-acp README](https://cdn.jsdelivr.net/gh/agentclientprotocol/claude-agent-acp@main/README.md)
- JetBrains AIR extensions in claude-agent-acp: goals (`_meta.jetbrains.air.goal`), permission presentation (editable choices, durable effects), a compact diff patch, structured session failures, recommended model/effort defaults, a tool-call contract, and native subagent sessions (earlier RFD draft). — [claude-agent-acp README](https://cdn.jsdelivr.net/gh/agentclientprotocol/claude-agent-acp@main/README.md)
- **codex-acp**: the original `zed-industries/codex-acp` was archived on 2026-07-22, and development moved to `agentclientprotocol/codex-acp`, "built on the new Codex App Server". — [zed-industries/codex-acp](https://github.com/zed-industries/codex-acp)
- The current codex-acp starts the Codex App Server and translates ACP to and from it, bundling `@openai/codex` (`CODEX_PATH` can override). It supports approvals/sandbox config, plans, terminal events (background terminal tasks can be listed and stopped in AIR), slash commands (`/status`, `/mcp`, `/skills`, `/goal`, `/review`, `/review-branch`, `/review-commit`, `/compact`, `/logout`), client MCP servers (stdio and HTTP), modes via `INITIAL_AGENT_MODE` (`read-only|workspace-write|agent|agent-full-access`), model/reasoning-effort/fast mode, token usage events, steering via `_session/steering`, goals (AIR), and native subagent sessions. — [agentclientprotocol/codex-acp](https://github.com/agentclientprotocol/codex-acp)
- The **`_session/steering`** extension (pre-standard, shipped by both codex-acp and claude-agent-acp; standardization in agent-client-protocol PR #1261) is advertised as `_meta.steering={supported:true}` and takes `sessionId`, `prompt` (content blocks) and optional `_meta.steering.idleBehavior`. Outcomes: `injected` (joined the running turn), `startedNewTurn` (no turn running, so one was started), `promptRequired` (opt-in: the host keeps the input and sends it later via normal `session/prompt`), and `failed`. Steers are serialized per session and run concurrently across sessions. — [codex-acp steering.md](https://cdn.jsdelivr.net/gh/agentclientprotocol/codex-acp@main/docs/steering.md)
- **Copilot CLI ACP**: public preview since 2026-01-28. Clients can initialize, discover capabilities, and create isolated sessions with their own working directories. — [GitHub changelog 2026-01-28](https://github.blog/changelog/2026-01-28-acp-support-in-copilot-cli-is-now-in-public-preview/)
- Copilot ACP details: `copilot --acp --stdio` (default; the server exits when stdin closes) or `--port <n>` (TCP on 127.0.0.1, multi-connection). **Server-wide** flags fixed at startup: `--available-tools`, `--excluded-tools`, `--effort/--reasoning-effort` (`low..max`), `--sandbox/--no-sandbox` (enterprise policy overrides). `session/new` accepts cwd and MCP servers, and sessions can be resumed. Slash commands are advertised via `available_commands_update` (built-ins plus user-invocable skills). Interactive commands (`/diff`, `/resume`, `/settings`, `/login`, `/help`) don't work over ACP and are sent to the model as text. `/usage` returns output without invoking the model. Clients can't change tool filtering or reasoning per session. BYOK (`COPILOT_PROVIDER_*`) works without a GitHub login. — [GitHub Docs: ACP server](https://docs.github.com/en/copilot/reference/copilot-cli-reference/acp-server)
- **Gemini CLI**: `gemini --acp` starts ACP mode (JSON-RPC over stdio) for IDE integrations. — [Gemini CLI ACP mode](https://geminicli.com/docs/cli/acp-mode/). A third-party PR claims `@google/gemini-cli@0.50.0` made `--acp` stable and deprecated `--experimental-acp` — [secondary: codeoid PR](https://github.com/highflame-ai/codeoid/pull/143/files) (unverified).
- **OpenHands**: `openhands acp` runs the OpenHands CLI as an ACP server (supports `--resume`; ACP since CLI 1.3.0; IDE integration labeled experimental). — [OpenHands CLI IDE docs](https://docs.openhands.dev/openhands/usage/cli/ide/overview) (from search snippet). OpenHands also acts as an ACP **client**: the SDK's `ACPAgent` and the browser-based "Agent Canvas" drive any ACP agent and reuse that agent's subscription credentials (2026-06-18). — [OpenHands blog](https://openhands.dev/blog/use-any-coding-agent-in-openhands-with-acp)

**Vendor-native protocols the adapters sit on (for gap comparison)**
- The Codex app-server exposes `turn/steer`, `turn/interrupt`, `thread/fork` (`ephemeral`, `lastTurnId`), `thread/goal/set|get|clear`, `review/start`, `thread/backgroundTerminals/list|clean|terminate` (experimental), `account/rateLimits/read` plus the `account/rateLimits/updated` notification (windows with `usedPercent`, `windowDurationMins`, `resetsAt`), `thread/tokenUsage/updated`, `turn/diff/updated`, `turn/plan/updated`, `model/list`, `skills/list`, `hooks/list`, MCP status/OAuth, `config/*` and `fs/*`. — [Codex App Server docs](https://learn.chatgpt.com/docs/app-server)
- The Claude Agent SDK `Query` (streaming-input mode) exposes `interrupt()` (returns `still_queued`/`cancelled` receipts on CLIs advertising `interrupt_receipt_v1`), `setPermissionMode`, `setModel`, `streamInput`, `supportedCommands/Models/Agents`, `mcpServerStatus`, `backgroundTasks()` ("same as pressing Ctrl+B"), `stopTask(taskId)`, `getContextUsage()`, `accountInfo()`, `rewindFiles()` and `close()`. It also has a `promptSuggestions` option (emits `prompt_suggestion` messages). — [Claude Agent SDK TS reference](https://code.claude.com/docs/en/agent-sdk/typescript.md)
- The Copilot SDK (now being renamed "Microsoft Copilot SDK") is GA with semver: an SDK client talks JSON-RPC to Copilot CLI in server mode, manages the CLI process lifecycle or connects to an external CLI server, and its permission handler governs tools. Languages: TS, Python, Go, .NET, Java, Rust. — [Copilot SDK README](https://cdn.jsdelivr.net/gh/github/copilot-sdk@main/README.md). The headless external server (`copilot --headless --port 4321`, client `cliUrl`) and the claim that "the same server … powers the GitHub Copilot app" are from secondary sources — [secondary: InfoWorld](https://www.infoworld.com/article/4125776/building-ai-agents-with-the-github-copilot-sdk.html).
- OpenAI built the app-server after trying to expose Codex as an MCP server and finding MCP semantics hard to make work for VS Code. InfoQ notes ACP aims to be universal while the app-server is Codex-specific. — [OpenAI: Unlocking the Codex harness (2026-02-04)](https://openai.com/index/unlocking-the-codex-harness); [InfoQ](https://www.infoq.com/news/2026/02/opanai-codex-app-server)

### Inferences
- **Single integration is feasible for the baseline but lossy at the edges.** machdoch could replace its one-shot JSONL parsing with an ACP client and get persistent sessions, cancel without kill (`session/cancel`, `session/close`), real permission requests, plans, tool-call updates, slash command lists, config options (model/mode/effort), `session/list|resume`, and `usage_update` (context fill + cost) for all three CLIs.
- **Gap list vs vendor-native, for machdoch's planned features:**
  - Rate limits: no ACP primitive. Codex has `account/rateLimits/*`; Copilot `/usage` is a text command.
  - Prompt suggestions: no ACP primitive (none in the RFD index).
  - Steering: only the `_session/steering` extension, in claude-agent-acp and codex-acp; I found no evidence Copilot `--acp` supports it.
  - Goals: AIR extension / Codex `/goal`.
  - Review: only as Codex slash commands.
  - Background-task list/stop: AIR-only extension in codex-acp; v2 display terminals.
  - Subagent sessions: draft RFD.
- **Adapters add a hop and a lag.** claude-agent-acp wraps the Agent SDK, which wraps the CLI, and codex-acp wraps the app-server, so new vendor features land natively first and in ACP later. Both adapters are Node packages, which matters for a Tauri/Rust host: it either needs Node available or uses the CLIs' own protocols. The ACP Rust SDK reached 1.0 on 2026-06-25.
- **Recommended architecture (inference): a hybrid like JetBrains AIR's.** Use ACP as the common session/turn/permission/tool-call model, and negotiate vendor extensions (`_session/steering`, `_meta` for goals/usage) or call native side-channels when present. The alternative is three native drivers (Claude Agent SDK stream-json control protocol, Codex app-server, Copilot SDK/ACP) normalized behind machdoch's own internal model. ACP's schema (v2 `state_update`, stop reasons, `usage_update`, notices, compaction) is a good template for that internal model either way.
- The v2 lifecycle (prompt accepted, `running`/`requires_action`/`idle`, background activity allowed while idle) maps well onto machdoch's task queue and "needs attention" states.

### Gaps
- I could not confirm whether Copilot CLI's ACP server implements `session/list`, `session/load` vs `session/resume`, `usage_update`, plans, or terminals. GitHub's page mentions only that sessions "can be resumed"/"loads".
- Release versions and dates of claude-agent-acp and codex-acp weren't visible on the GitHub pages I fetched.
- The exact Gemini CLI version that made `--acp` stable is unverified.
- I didn't read the session-usage RFD in full. Whether ACP plans to cover rate-limit windows is unknown; the stabilized `usage_update` covers only context size and cost.

## Q2. How established hosts implement persistent sessions, parallel/background agents, steering/queueing, approvals, diff review, cost/usage and follow-ups

### Takeaway
Hosts fall into three groups.
- **ACP hosts** (Zed, JetBrains Air / Air in IDEs, OpenHands Agent Canvas) treat the agent as owning auth, models and billing. They add registry install, thread history import, permission UI, and (Air) worktree or Docker isolation, and they use vendor extensions for steering, goals and background tasks.
- **Vendor-native hosts** (VS Code with the Claude Agent SDK and Codex extension / "Agent Host"; Codex app, IDE extensions, JetBrains and Xcode via the app-server; Claude Code desktop/web/remote) get the richest UX: queue and steer, fork, compaction display, rate-limit display, and background sessions.
- **Orchestrators** (Conductor, Nimbalyst/Crystal, Sculptor, Claude Squad, Warp) sell parallelism through per-task git worktrees or containers, plus diff/PR review and "needs input" notifications. Most add little protocol-level control.

### Cited Findings
**Zed (ACP originator)**
- External agents connect over ACP. Zed hosts the thread (Agent Panel / Threads Sidebar) while the agent owns runtime, auth, model selection, tools and config. "Terminal Threads" are a separate option for running a CLI/TUI directly. — [Zed External Agents](https://zed.dev/docs/ai/external-agents)
- The ACP Registry (`zed: acp registry`) is the install path; extension-provided agents are deprecated and auto-migrated. Custom agents are `agent_servers` entries (`command`, `args`, `env`). Zed MCP servers "may be forwarded over ACP", and tool permissions are a "mix of Zed/ACP forwarding and agent-native rules". Zed can **import existing sessions** from external agents into Thread History. `dev: open acp logs` is the protocol debugger. Zed doesn't charge for external agents. — [Zed External Agents](https://zed.dev/docs/ai/external-agents)
- The ACP Registry has been the preferred install route since Zed v0.221.x, and Zed switched its Claude adapter package from `claude-code-acp` to `claude-agent-acp`. — [secondary mirror of Zed commits](https://git.secluded.site/zed/commit/4dac6bd6d74de2ad37d17c0f97f50fb8290a689f); [commit](https://git.secluded.site/zed/commit/f64484a9e384ef82d2856fa66c149e4776e302ea)

**JetBrains Air / Air in IDEs (ACP)**
- Air (public preview, March 2026) is an "agentic development environment" for delegating tasks to several agents in parallel; it supports Codex, Claude Agent, Gemini CLI and Junie out of the box, plus others via ACP. — [JetBrains Air blog (2026-03)](https://blog.jetbrains.com/air/2026/03/12/air-launches-as-public-preview/) (blog returned 403; via search summary). A July 2026 post adds GitHub Copilot, OpenCode, Pi, Cline and other ACP agents — [JetBrains Air July update](https://blog.jetbrains.com/air/2026/07/what-s-new-air-gets-more-agents-local-models-and-java-kotlin-code-intelligence/) (title/snippet only).
- Execution environments: **Local** (edits the working dir directly), **Git Worktree** (per-task branch; `.air/worktree.json`), **Docker** (isolated container; `.air/docker.json`). Permission modes: Ask Permission, Auto-Edit, Plan, Full Access. The agent pauses and notifies you when it needs a decision, and `⌘+1` shows all task states. There is a built-in web preview that auto-starts the dev server. You can change model but not provider within a task. — [secondary review, 2026-05-06](https://recca0120.github.io/en/2026/05/06/jetbrains-air-agentic-ide/)
- "Air in IDEs" (EAP, Oct 2026): parallel sessions across projects with unread updates, changed files and outgoing commits tracked; sessions run in the agent panel or a terminal view; **local-to-cloud handoff** ("cloud agents that keep working when your laptop is closed", followed on web/mobile via Air Teams); diffs opened from the session with **line comments sent back to the agent**; auto-detection of installed agents plus a registry. — [JetBrains Air in IDEs](https://www.jetbrains.com/air/ides/); [JetBrains AI blog Oct 2026](https://blog.jetbrains.com/ai/2026/10/air-in-ides-eap/) (title only)
- AIR drives codex-acp/claude-agent-acp extensions: goals, an "Async Tasks panel" for background terminals with targeted stop, permission presentation with editable choices and durable effects, a compact diff patch, structured errors, and recommended model/effort defaults. — [agentclientprotocol/codex-acp](https://github.com/agentclientprotocol/codex-acp); [claude-agent-acp README](https://cdn.jsdelivr.net/gh/agentclientprotocol/claude-agent-acp@main/README.md)

**VS Code (vendor-native, multi-harness)**
- Agents run on the GitHub Copilot, Claude or Codex **harness**, across local Chat view, an **Agents window** (for delegating and coordinating across projects), cloud sessions (experimental; managed compute, machine can be offline), cloud automations (preview), and remote sessions via GitHub Environments (preview; continue from VS Code, Copilot app, Copilot CLI, GitHub.com, Mobile). You can steer or stop a request. "A worktree isolates code changes but isn't a security boundary." — [VS Code Agents overview](https://code.visualstudio.com/docs/copilot/agents/overview)
- Claude: "The Anthropic Claude Agent SDK is integrated into VS Code." Sessions run in the workspace or an isolated worktree and are billed via Copilot or BYOK. Codex runs via the OpenAI Codex extension in Chat view, or via an experimental "Agent Host" in the Agents window without the extension (`chat.editor.codex.preferAgentHost`). Claude/Codex sessions can receive handoffs from Local sessions but can't hand off onward or to cloud. They are disabled under certain managed permission/sandbox enterprise settings. — [VS Code third-party agents](https://code.visualstudio.com/docs/copilot/agents/third-party-agents)
- VS Code 1.110 (Feb 2026 release): Claude agent sessions got **steering and queuing**, renaming, context-window rendering with compaction, a `getDiagnostics` tool, and `/compact`, `/agents`, `/hooks`. You can steer without answering a pending question carousel. `/fork` and "Fork Conversation" exist. Tasks can be handed off to Copilot CLI (background) and tracked in VS Code. `/autoApprove` (`/yolo`) toggles global auto-approve, and terminal sandboxing (preview) is suggested as a safeguard. — [VS Code 1.110 release notes](https://code.visualstudio.com/updates/v1_110); [GitHub changelog 2026-03-06](https://github.blog/changelog/2026-03-06-github-copilot-in-visual-studio-code-v1-110-february-release/)
- 1.123 (June 2026) added the Agents window and agent session sync; 1.128 added multiple chats inside a Claude agent-host session. — [secondary: Visual Studio Magazine 1.123](https://visualstudiomagazine.com/articles/2026/06/04/vs-code-1-123-adds-agent-session-sync-1m-context-windows.aspx); [VSM 1.128](https://visualstudiomagazine.com/articles/2026/07/08/claude-ai-gets-yet-another-boost-in-vs-code-1-128.aspx)
- Chat participants (the old extension API) "are deprecated and are not supported in the Copilot harness". — [VS Code chat extension guide](https://code.visualstudio.com/api/extension-guides/ai/chat)

**OpenAI Codex app-server consumers**
- The app-server "powers rich clients, such as the Codex VS Code extension". Transports: stdio JSONL (default), WebSocket (`--listen ws://`, experimental, with `/readyz` and `/healthz`, rejects `Origin` headers), and Unix socket. Primitives are Thread > Turn > Item. Lifecycle: `initialize` (with `clientInfo` for compliance logs) → `initialized` → thread start/resume/fork → `turn/start` → stream until `turn/completed`. `turn/start` accepts per-turn overrides and an **`outputSchema`**. Clients can opt out of notification methods. Experimental APIs sit behind `capabilities.experimentalApi`. TS types and JSON schema are generated per Codex version (`codex app-server generate-ts|generate-json-schema`). — [Codex App Server docs](https://learn.chatgpt.com/docs/app-server)
- The app-server powers the CLI, VS Code extension, web app, macOS desktop app, and the JetBrains and Xcode integrations. Local clients spawn a platform binary as a child process over stdio, and Xcode can point at newer server binaries independently of its own releases. — [InfoQ 2026-02](https://www.infoq.com/news/2026/02/opanai-codex-app-server); [OpenAI blog](https://openai.com/index/unlocking-the-codex-harness)
- Approvals are server→client requests. `item/commandExecution/requestApproval` takes decisions `accept`, `acceptForSession`, `decline`, `cancel`, or `acceptWithExecpolicyAmendment`; `item/fileChange/requestApproval` takes `accept`, `acceptForSession`, `decline`, `cancel`. Both are followed by `serverRequest/resolved`. Other server requests: `item/permissions/requestApproval` (network/fs grants), `mcpServer/elicitation/request`, `tool/requestUserInput` (experimental). — [Codex App Server docs](https://learn.chatgpt.com/docs/app-server)
- Live UX signals: `turn/diff/updated` (aggregated unified diff per turn), `turn/plan/updated` (steps `pending|inProgress|completed`), `thread/tokenUsage/updated`, `account/rateLimits/updated`, `thread/status/changed`, `thread/name/updated`, `thread/goal/updated`. — [Codex App Server docs](https://learn.chatgpt.com/docs/app-server)
- Codex app (desktop, now part of the ChatGPT app for macOS/Windows/Linux): scheduled tasks (standalone or inside a chat), long-running work, Chat vs Work modes. — [Codex/ChatGPT app docs](https://learn.chatgpt.com/docs/app). Users report "Queued follow-up inputs" are applied after the current turn finishes — [secondary: OpenAI community](https://community.openai.com/t/i-find-this-new-queued-follow-up-inputs-feature-a-little-frustrating/1398627).
- Codex CLI: press Tab while Codex is running to queue follow-up text, slash commands or `!` commands for the next turn. — [Codex CLI features](https://developers.openai.com/codex/cli/features) (search snippet; the page now redirects)

**Claude Code surfaces (vendor-native)**
- Queueing: Enter while Claude works queues the message. ## Q3. Follow-up prompt suggestion patterns: who shows suggested next prompts and how they are generated

### Takeaway
The only clearly documented after-turn next-prompt feature among the target CLIs is **Claude Code's prompt suggestions**. It is a native agent feature: a short background request to the session's own model that reuses the prompt cache. It is exposed to hosts as a `prompt_suggestion` message (SDK `promptSuggestions: true`, or `--prompt-suggestions` with stream-json). Codex documents "context-aware suggestions" only at session start or return. VS Code 1.110 has start-of-session "contextual tips". ACP has no suggestion primitive. For Codex and Copilot, a host must generate suggestions itself, ideally with a cheap side call. Codex's `thread/fork` (ephemeral) plus `outputSchema` makes that pattern easy.

### Cited Findings
- Claude Code: "After Claude responds, Claude Code can suggest your next prompt based on your conversation history". Tab or Right-arrow accepts, typing dismisses. Generated "with a short background request to the same model your session is using… Because it reuses the conversation's prompt cache, it is mostly cache reads plus a few output tokens". — [Claude Code interactive mode](https://code.claude.com/docs/en/interactive-mode.md)
- Claude Code skips suggestions when the prompt cache is cold, after the first turn in some sessions, after an error, in plan mode, near the usage limit (override with `CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=true`, v2.1.238+), and for agent-team teammates. It shows suggestions less often if many go unused ("Showing fewer prompt suggestions · use one to bring them back"). It is off by default for third-party providers or gateways (no feature-flag fetch). Disable with `/config`, `promptSuggestionEnabled:false`, or the env var. — [Claude Code interactive mode](https://code.claude.com/docs/en/interactive-mode.md)
- Headless: "Pass `--prompt-suggestions` with `-p "<prompt>" --output-format stream-json --verbose` to have Claude Code emit a `prompt_suggestion` message after each turn that generates one". Short conversations and cold caches may produce none. — [Claude Code interactive mode](https://code.claude.com/docs/en/interactive-mode.md)
- Agent SDK: `promptSuggestions` (boolean, default false). "After a turn, Claude Code emits a `prompt_suggestion` message carrying a predicted next user prompt." — [Claude Agent SDK TS reference](https://code.claude.com/docs/en/agent-sdk/typescript.md)
- Claude Code also shows a grayed example prompt at session start, picked from the project's git history. — [Claude Code interactive mode](https://code.claude.com/docs/en/interactive-mode.md)
- Codex app: "context-aware suggestions surface follow-ups and tasks you may want to resume when you start or return to Codex". — [Codex app settings](https://developers.openai.com/codex/app/settings) (search snippet)
- VS Code 1.110: no after-response follow-ups documented. Experimental "contextual tips" appear when a new chat session starts. — [VS Code 1.110 release notes](https://code.visualstudio.com/updates/v1_110). GitHub docs mention clicking "suggested prompts" in the chat box without saying how they're generated — [GitHub Docs: chat in IDE](https://docs.github.com/en/copilot/how-tos/chat-with-copilot/chat-in-ide) (search snippet).
- Sculptor's "Suggestions (beta)" are code-fix suggestions on agent output, not next-prompt suggestions. — [Imbue Sculptor](https://imbue.com/sculptor)
- Codex app-server `turn/start` supports `outputSchema`, and `thread/fork` supports `ephemeral`/`lastTurnId`. — [Codex App Server docs](https://learn.chatgpt.com/docs/app-server)
- ACP's RFD index has no prompt-suggestion RFD. — [ACP llms.txt](https://agentclientprotocol.com/llms.txt)

### Inferences
- **Three generation strategies are available to machdoch:**
  - **(a) Native.** Claude only: enable `--prompt-suggestions` / `promptSuggestions` and render `prompt_suggestion`. This is the cheapest, since the cache is reused, and it respects plan limits.
  - **(b) Side call on a forked ephemeral thread.** Codex: `thread/fork` with `ephemeral:true` plus a `turn/start` whose `outputSchema` returns `{suggestions:[...]}`. This keeps the main thread clean and reuses context. Claude: `forkSession` / `persistSession:false` gives a similar route.
  - **(c) Separate cheap model call** from machdoch over the transcript. This works for Copilot and any ACP agent, but costs uncached tokens and needs the user's own API key or routing.
- Copy Claude's skip heuristics regardless of strategy: no suggestions after errors, in plan mode, near rate limits, or on cold caches, and back off after repeated ignores. They keep cost and annoyance low.
- Asking the main agent to emit suggestions as a structured field in its final answer is possible, but it pollutes the transcript and the context. The fork-based approaches look cleaner.

### Gaps
- No primary documentation found for after-turn suggested prompts in Codex, Copilot CLI, Zed, JetBrains Air, Cursor or Conductor.
- How VS Code's suggested prompts are generated is undocumented in the sources reached.
- Copilot CLI and the Copilot SDK show no evidence of a suggestion event.

## Q4. Background agents: long-running work patterns (worktrees, notifications, resumable sessions, cloud handoff) and how hosts surface agent-spawned background processes

### Takeaway
The converging pattern has five parts:
- one isolated workspace per task (a git worktree by default; Docker, container or microVM when safety matters);
- a supervisor that keeps sessions alive independently of the UI and resumes them from saved transcripts;
- a status roster with "needs input" notifications;
- optional handoff to cloud execution;
- first-class APIs for agent-spawned background shells and subagents (list, output, stop).

Claude Code (agent view supervisor, background Bash, `/tasks`, SDK `backgroundTasks`/`stopTask`/task notifications) and the Codex app-server (`thread/backgroundTerminals/*`, `command/exec`, `process/*`) expose this natively. ACP v2 only models "idle while background activity continues", and codex-acp exposes background terminal list/stop only through AIR extensions.

### Cited Findings
- Claude agent view runs a **supervisor process** that keeps sessions alive after you close the terminal and restarts crashed workers. Idle unattached sessions (~1h) are stopped but resume from disk on attach. Sessions survive auto-updates and sleep. State is read via `claude agents --json`. Dispatched sessions move into their own git worktree under `.claude/worktrees/` once they start editing. Before finishing, a session is instructed to commit, push and optionally open a draft PR, and it never pushes to main or force-pushes. Deletion keeps worktrees that have uncommitted or unpushed work. — [Claude Code agent view](https://code.claude.com/docs/en/agent-view.md)
- Claude agent view notifications go through the terminal channel and fire the `Notification` hook with types `agent_needs_input` / `agent_completed`. — [Claude Code agent view](https://code.claude.com/docs/en/agent-view.md)
- Claude background Bash: Ctrl+B or a request backgrounds a command, which returns a task ID. Tasks are viewed and stopped in `/tasks`, cleaned up on exit (including detached `setsid` children on macOS/Linux), and killed at 5GB of output. There's no time limit in interactive sessions, but there is one in unattended `-p`/cloud runs. A foreground subagent's background commands end with that subagent. — [Claude Code interactive mode](https://code.claude.com/docs/en/interactive-mode.md)
- Claude SDK: `backgroundTasks(toolUseId?)`, `stopTask(taskId)`, `SDKTaskNotificationMessage` (emitted when a backgrounded task finishes), `SDKTaskProgressMessage` (with `summary` when `agentProgressSummaries` is on). — [Claude Agent SDK TS reference](https://code.claude.com/docs/en/agent-sdk/typescript.md)
- Codex app-server: `thread/backgroundTerminals/list`, `clean`, `terminate` (experimental); `command/exec` with `write`/`resize`/`terminate` and streamed `command/exec/outputDelta`; `process/*` (experimental, outside sandbox) with `process/outputDelta` and `process/exited`. — [Codex App Server docs](https://learn.chatgpt.com/docs/app-server)
- codex-acp: in AIR, background terminals continue after the turn and show in an **Async Tasks panel** with task status and targeted stop after capability negotiation. — [codex-acp README](https://cdn.jsdelivr.net/gh/agentclientprotocol/codex-acp@main/README.md)
- claude-agent-acp: background commands keep running after cancel. Background subagent children survive a parent cancel unless stopped (`perTaskStopAffordance`). — [claude-agent-acp README](https://cdn.jsdelivr.net/gh/agentclientprotocol/claude-agent-acp@main/README.md)
- ACP v2: `idle` = "no foreground work is active. Background activity may continue". Background completion doesn't start foreground work by itself, and an agent's reaction to it must report `running` then `idle`. — [ACP v2 Prompt Lifecycle](https://agentclientprotocol.com/protocol/v2/prompt-lifecycle.md)
- Cloud handoff: Air in IDEs hands long tasks to cloud agents and lets you follow them on web/mobile (Air Teams) — [JetBrains Air in IDEs](https://www.jetbrains.com/air/ides/). VS Code has cloud sessions (experimental) and remote sessions via GitHub Environments, and a cloud task can continue in Copilot CLI — [VS Code Agents overview](https://code.visualstudio.com/docs/copilot/agents/overview). Claude Remote Control continues a local session from other devices with push notifications for required actions — [Claude Code Remote Control](https://code.claude.com/docs/en/remote-control.md).
- Isolation choices: Air offers Local / Worktree / Docker per task — [secondary review](https://recca0120.github.io/en/2026/05/06/jetbrains-air-agentic-ide/). Sculptor uses containers instead of worktrees — [Imbue Sculptor](https://imbue.com/sculptor). Claude Squad uses tmux plus worktrees with pause/resume — [Claude Squad](https://github.com/smtg-ai/claude-squad). Conductor gives each task its own workspace/branch/terminal — [Conductor docs](https://www.conductor.build/docs/).
- Scheduled background work: Codex app scheduled tasks — [Codex app docs](https://learn.chatgpt.com/docs/app); OpenHands Agent Canvas automations — [OpenHands blog](https://openhands.dev/blog/use-any-coding-agent-in-openhands-with-acp); VS Code cloud/local automations — [VS Code Agents overview](https://code.visualstudio.com/docs/copilot/agents/overview).
- Air's built-in web preview auto-launches the dev server. — [secondary review](https://recca0120.github.io/en/2026/05/06/jetbrains-air-agentic-ide/)

### Inferences
- machdoch's current "kill on cancel" model loses agent-spawned dev servers and watchers, and loses session state. With long-lived sessions it should do the following:
  1. Cancel via protocol (`session/cancel`, `turn/interrupt`, SDK `interrupt()`) and keep the process alive.
  2. Show a per-session **background processes panel** fed by Claude `task_notification`/`task_progress` plus `/tasks`-equivalent SDK calls, and by Codex `thread/backgroundTerminals/list` and `command/exec` streams, with explicit stop buttons (`stopTask`, `backgroundTerminals/terminate`).
  3. Decide a policy for what survives cancel versus session close. Both adapters keep background commands running after cancel.
- machdoch's existing queue and scheduler could adopt the Claude supervisor approach: one long-lived CLI process per active chat, stopped after idle and resumed from transcript via `resume` / `thread/resume` / `session/resume`. That bounds resource use with many chats.
- Worktree isolation is now table stakes for parallel modes. Hosts label it as code isolation, not security isolation (VS Code says so explicitly). Containers or microVMs are the security tier.

### Gaps
- No documented API in Copilot CLI ACP or the Copilot SDK for listing or stopping agent-spawned background shells was found.
- I didn't verify how Codex app or Conductor visually surface dev servers.
- The Claude Desktop app's handling of background sessions wasn't covered (the agent view docs cover the terminal).

## Q5. Security and isolation when moving from bypass-permissions to interactive approvals

### Takeaway
Hosts layer three things:
- **OS sandboxing** of agent-run commands. Codex: Seatbelt, bubblewrap, and a native Windows sandbox. Claude Code: Seatbelt or bubblewrap, but **no native Windows sandbox**, WSL2 only.
- **Approval policies** where the agent asks only when crossing the sandbox boundary (Codex `on-request`; Claude sandbox auto-allow).
- **Host-side approval UIs** with scoped grants (accept once, for session, or a persistent rule amendment), plus project-level isolation (worktree, Docker, container).

ACP's own guidance: permission requests are advisory, agent text is untrusted, and the client must sanitize rendering and links. When a turn is cancelled, the client must resolve pending permission requests.

### Cited Findings
- ACP security considerations:
  - "ACP itself does not sandbox" the agent.
  - Permission requests are advisory; the agent must honor the decision.
  - Treat agent-authored strings, URIs and paths as untrusted, including replayed content.
  - `clientInfo`/`agentInfo` are self-reported and shouldn't drive security decisions.
  - Don't read `file:` URIs outside the workspace roots without user action.
  - Neutralize terminal control sequences.
  - Don't auto-fetch remote images or run scripts from agent content; reveal bidi and zero-width characters in commands, paths, diffs and permission prompts.
  - Agent slash commands should look distinct from client commands.
  - No credentials in `_meta`.
  - Intermediaries shouldn't answer permission requests except under user-configured policy.
  - Multi-user agents must scope session list, load and permissions to the owner.
  — [ACP Security Considerations](https://agentclientprotocol.com/protocol/v1/security.md)
- Codex sandboxing: modes are `read-only`, `workspace-write` (default) and `danger-full-access`. Approval policies are `on-request` (work inside the sandbox, ask to go beyond) and `never`; "untrusted is no longer selectable". `approvals_reviewer` = `user` | `auto_review` (a reviewer agent). OS: macOS Seatbelt; Linux/WSL2 bubblewrap; **Windows native sandbox in PowerShell**. Recommendations: extend `writable_roots` instead of removing the sandbox, use command-prefix rules, keep the project as the boundary, and pick the narrowest approval scope. — [Codex sandboxing](https://learn.chatgpt.com/docs/sandboxing)
- Codex approval decisions include `acceptForSession` and `acceptWithExecpolicyAmendment` (a persistent rule). — [Codex App Server docs](https://learn.chatgpt.com/docs/app-server)
- Codex app-server WebSocket: non-loopback listeners allow unauthenticated connections by default during rollout, so set `--ws-auth capability-token`. The server rejects requests with an `Origin` header. — [Codex App Server docs](https://learn.chatgpt.com/docs/app-server)
- Claude Code sandbox:
  - Off by default. It covers Bash, PowerShell and Monitor commands only; file tools, MCP servers and hooks run outside it.
  - macOS Seatbelt; Linux/WSL2 bubblewrap plus socat; **"Native Windows: not supported. Commands run unsandboxed. Use WSL2"**.
  - Writes are limited to the cwd, temp and `--add-dir`, with protected paths (`.claude/settings*`, `.mcp.json`, `.git/hooks`, `~/.claude`, `.vscode`, `.idea`). Reads are broadly allowed by default, including `~/.ssh`.
  - Network goes through a local proxy with `allowedDomains` (empty by default). Credentials can be masked.
  - Auto-allow runs sandboxed Bash without prompts even in Manual mode.
  - The `dangerouslyDisableSandbox` retry is approved per mode; `allowUnsandboxedCommands:false` plus `failIfUnavailable:true` makes a strict baseline.
  - It builds on the open-source `@anthropic-ai/sandbox-runtime`, which can wrap the whole CLI process.
  — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing.md)
- Claude SDK: `canUseTool` fires only on fall-through prompts. `permissionPrompts:'host'|'none'`. Pending permission requests are re-delivered after `reinitialize()`, so handlers must be idempotent per request ID. — [Claude Agent SDK TS reference](https://code.claude.com/docs/en/agent-sdk/typescript.md)
- Copilot ACP: `--sandbox/--no-sandbox` (an enterprise sandbox policy overrides `--no-sandbox`); tool allow/deny lists are server-wide only. — [GitHub Docs: ACP server](https://docs.github.com/en/copilot/reference/copilot-cli-reference/acp-server)
- VS Code: global auto-approve (`/yolo`) "skips all tool confirmation prompts", and terminal sandboxing (preview) is suggested — [VS Code 1.110](https://code.visualstudio.com/updates/v1_110). "A worktree isolates code changes but isn't a security boundary" — [VS Code Agents overview](https://code.visualstudio.com/docs/copilot/agents/overview). Claude/Codex harnesses are disabled under managed permission/sandbox enterprise settings — [VS Code third-party agents](https://code.visualstudio.com/docs/copilot/agents/third-party-agents).
- Permission-mode presets in hosts: Air uses Ask Permission / Auto-Edit / Plan / Full Access — [secondary review](https://recca0120.github.io/en/2026/05/06/jetbrains-air-agentic-ide/). codex-acp uses `read-only` / `workspace-write` / `agent` / `agent-full-access` — [codex-acp](https://github.com/agentclientprotocol/codex-acp). AIR adds "permission presentation, editable choices, and durable effects" — [claude-agent-acp README](https://cdn.jsdelivr.net/gh/agentclientprotocol/claude-agent-acp@main/README.md).
- Claude Remote Control security model: outbound HTTPS only, no inbound ports, TLS via the Anthropic API, multiple short-lived single-purpose credentials. Enterprise roles and Trusted Devices gate access. — [Claude Code Remote Control](https://code.claude.com/docs/en/remote-control.md)
- Containers as a safety tier: Sculptor ("containers keep your machine safe", unlike worktrees) — [Imbue Sculptor](https://imbue.com/sculptor); Air Docker mode — [secondary review](https://recca0120.github.io/en/2026/05/06/jetbrains-air-agentic-ide/).

### Inferences
- **For machdoch (a Windows/Tauri app):**
  - Leaving bypass mode should start with a small set of host-level presets (Read-only/Plan, Ask, Auto-edit, Full access) mapped per CLI. Claude: `permissionMode` plus sandbox settings. Codex: `sandbox_mode` × `approval_policy` (prefer `workspace-write` + `on-request`). Copilot: `--sandbox` and tool lists, fixed per process.
  - Copilot's settings are server-wide, so per-chat permission differences need one Copilot process per policy.
  - On native Windows, Claude Code's Bash sandbox is unavailable. Codex has a native Windows sandbox. Claude chats on Windows will therefore rely on approvals, or on WSL2 or containers, for real isolation. The UI should state this rather than imply equal safety.
- **Approval UI pattern:**
  - Offer one-time, for-this-session, and persistent-rule options, mirroring Codex `accept` / `acceptForSession` / `acceptWithExecpolicyAmendment` and Claude allow rules.
  - Show the exact command, cwd and paths with invisible characters revealed (ACP guidance).
  - Route approvals into machdoch's existing attention/notification system, with a "Needs input" state like Claude agent view and Air.
  - Answer pending approvals with "cancelled" when a turn is stopped (ACP v2).
- **Fleet:** remote approval from another device follows Claude Remote Control's push-on-"actions required" pattern. Any remote transport should require token auth and reject browser Origins, as the Codex WebSocket does. Never let a relay auto-answer permissions except under explicit user policy (ACP).
- Bypass mode remains useful for scheduled or unattended runs, but hosts pair it with isolation: worktree for code, container or VM for safety. machdoch's scheduler or goals runs could default to a worktree, with an optional container tier.

### Gaps
- I couldn't fetch the Codex native Windows sandbox page (404), so implementation details (elevated vs unelevated, restricted tokens) and limitations are unverified here.
- I didn't verify whether Copilot CLI's `--sandbox` works on native Windows.
- I found no source describing how Zed renders ACP permission requests in detail (always-allow persistence and scope).
