## 1. Streaming input mode / session lifecycle: keep a session open, send messages mid-turn, interrupt, change model/permission mode/thinking at runtime

### Takeaway
A host does not need the Node SDK to get the full feature set. The SDK itself runs `claude --output-format stream-json --verbose --input-format stream-json` and talks to it over stdin/stdout with `control_request`/`control_response` frames, and machdoch already speaks that protocol. If the host keeps stdin open, one process can carry a whole multi-turn chat. Mid-turn user messages have documented queueing semantics (`priority: "next"|"later"|"now"`), interrupts are graceful and come with a receipt (`interrupt`, optionally `cancel_queued`), and model, permission mode, effort and other settings can be changed at runtime (`set_model`, `set_permission_mode`, `apply_flag_settings`). All of this is documented SDK API, and the wire shapes are in the published `sdk.d.ts`.

### Inferences
- Moving machdoch from one process per turn to one process per chat is the single biggest unlock. It removes the history re-send, keeps the prompt cache warm, and enables suggestions, mid-turn input, graceful interrupt, runtime model/effort switching and background-task events, all over a protocol the host already partly implements (`initialize`).
- A minimal wire user message is `{"type":"user","message":{"role":"user","content":...},"parent_tool_use_id":null,"uuid":"<uuid>","origin":{"kind":"human"},"priority":"next"}`. Stamping a `uuid` makes interrupt receipts, `cancel_async_message`, rewind and fork addressable.
- For cancel, a safer escalation than killing the process tree right away: send `interrupt` (optionally `cancel_queued:true`), wait for the receipt and `result`, then SIGINT, and only then kill.
- The Rust host would have to reimplement the SDK's library-only helpers itself (listSessions, getSessionMessages, forkSession, tool()/createSdkMcpServer). Alternatively it could bundle a small Node sidecar running the official SDK.

### Gaps
- No standalone public spec of the raw stdin/stdout control protocol was found. The docs describe SDK methods, and the wire shapes come from `sdk.d.ts`. The raw-protocol stability guarantee for non-SDK hosts is undocumented.
- The `rapidFollowupPreempt` initialize flag (internal) looks related to preempting a turn on fast follow-ups. Its semantics were not verified.

## 2. Prompt suggestions: `promptSuggestions` option, when `prompt_suggestion` is emitted, gating conditions

### Takeaway
Prompt suggestions are a documented TS SDK option (`promptSuggestions: true`, sent on `initialize`) and a CLI flag (`--prompt-suggestions`, which requires `-p --output-format stream-json --verbose`). A `{type:"prompt_suggestion", suggestion, uuid, session_id}` message can arrive after a turn's `result`. The generator skips a turn under many conditions. In the 2.1.312 code, the one that explains machdoch's empty test is `early_conversation`: no suggestion until the transcript holds at least 2 assistant messages. So a one-turn Haiku test can never produce one. A cold prompt cache also blocks generation. `--no-session-persistence` and tool-less sessions are not gates in the code path that was inspected.

### Cited Findings
- `promptSuggestions` (`boolean`, default `false`): "After a turn, Claude Code emits a `prompt_suggestion` message carrying a predicted next user prompt. Claude Code generates no suggestion for some turns, such as while your account is close to or at its usage limit." — [TS reference, Options](https://code.claude.com/docs/en/agent-sdk/typescript#options)
- Message type: `SDKPromptSuggestionMessage = { type: "prompt_suggestion"; suggestion: string; uuid: UUID; session_id: string }`. — [TS reference](https://code.claude.com/docs/en/agent-sdk/typescript#sdkpromptsuggestionmessage)
- Ordering: "A small number of trailing system events, such as `prompt_suggestion`, can arrive after [the ResultMessage], so iterate the stream to completion rather than breaking on the result." — [How the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- CLI flag: `--prompt-suggestions` emits a `prompt_suggestion` "after each turn that generates one; very short conversations can produce none. Requires `--print`, `--output-format stream-json`, and `--verbose`." The CLI rejects the flag without `-p` and stream-json output. — [CLI reference](https://code.claude.com/docs/en/cli-reference); [local claude.exe 2.1.312](file:///C:/Users/ehrha/.local/bin/claude.exe)
- Documented skip conditions: cold prompt cache; "After the first turn of a conversation, in some sessions"; the previous response ended in an error; plan mode; account close to or at its usage limit (override with `CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=true`, v2.1.238+); agent-team teammates. In print mode: "The generator skips very short conversations and cold prompt caches here too, so a single short `-p` query can emit none." — [Interactive mode, When Claude Code skips suggestions](https://code.claude.com/docs/en/interactive-mode#prompt-suggestions)
- Kill switches: setting `promptSuggestionEnabled: false`, or env `CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=false`, which takes precedence over the setting. Interactive mode leaves suggestions off in sessions that don't fetch feature flags (third-party providers, gateways, the first session after an install or upgrade). — [Interactive mode](https://code.claude.com/docs/en/interactive-mode#prompt-suggestions); [Env vars](https://code.claude.com/docs/en/env-vars)
- Cost: each suggestion is "a short background request to the same model your session is using", mostly cache reads plus a few output tokens, and counts toward plan limits or API cost. — [Costs](https://code.claude.com/docs/en/costs); [Interactive mode](https://code.claude.com/docs/en/interactive-mode#prompt-suggestions)
- Local code, CLI 2.1.312, SDK/stream-json path (internal implementation, so these conditions can change without notice):

  - It skips with reason `host_paused` (set by the internal `set_prompt_suggestions_paused` control), or `not_user_started` when the turn origin is `scheduled`, `task_notification`, `auto_continuation`, `host_synthetic` or `system` (behind a server flag).

### Inferences
- The empty local test is explained by `early_conversation`: one turn without tools has one assistant message. Possibly the cache gate as well (that turn had cache_creation 3439 vs cache_read 649). A valid test needs a long-lived stream-json process, at least 2 turns (or a turn with tool calls), the same model, the next turn within the cache TTL, and reading past the `result` message.
- The current per-turn architecture (stdin closed, process killed shortly after the result) will rarely, if ever, get suggestions. Even when the conversation is long enough, the history is re-sent as prompt text, so the transcript the CLI sees only spans that single invocation.
- `--no-session-persistence` and `--tools ""` are not checked in the inspected gating code. Their effect is indirect at most, through conversation length and cache warmth.
- Suggestions are not generated for task-notification or scheduled turns (behind a server flag). A host should therefore expect them only after human-initiated turns.

### Gaps
- No changelog entry was found that introduces the `promptSuggestions` SDK option or the `--prompt-suggestions` flag, so the minimum version is unknown.
- The skip reason (`WL(reason,"sdk")`) is logged to telemetry. It was not verified whether `--debug` shows it to a host.
- The Python SDK has no documented `prompt_suggestions` option (TS only).

## 3. Background tasks: background Bash, background/async subagents, Monitor, task events, stop/output, detached sessions, `/loop`, `/schedule`

### Takeaway
In a stream-json session with stdin left open, background work is fully observable and controllable. The events are `task_started`, `task_progress`, `task_updated`, `task_notification` and `background_tasks_changed`. The controls are `stop_task`, `background_tasks` (Ctrl+B) and the public-type-but-undocumented `get_task_output`. In one-shot `-p` (stdin closed), the CLI itself waits up to a 10-minute idle cap for background work and kills what remains, which the host's own "kill after 10 s" step undercuts. Detached sessions (`--bg`, `claude agents`) cannot be combined with `-p` and are terminal/daemon-oriented; scripts read their state via `claude agents --json`. `/loop` and the cron tools work in-session. `/schedule` creates cloud "scheduled tasks" (formerly routines, research preview).

### Cited Findings
- `task_started` (`task_type` is `local_bash` for Bash and Monitor, `local_agent` for subagents, or `remote_agent`) carries `task_id`, `run_id` (SDK 0.3.292), `tool_use_id`, `description`, `is_backgrounded`, `spawn_depth` (0.3.238), `parent_task_id` (0.3.292) and `ambient` (0.3.247; "exclude ambient tasks from activity indicators"). — [TS reference, SDKTaskStartedMessage](https://code.claude.com/docs/en/agent-sdk/typescript#sdktaskstartedmessage)
- `task_progress` carries `usage {total_tokens, tool_uses, duration_ms}`, `last_tool_name`, and `summary`. For subagents, `summary` is present only with `agentProgressSummaries`. For backgrounded MCP calls, it carries the server's progress. — [TS reference, SDKTaskProgressMessage](https://code.claude.com/docs/en/agent-sdk/typescript#sdktaskprogressmessage)
- `task_updated` carries `patch {status: pending|running|completed|failed|killed, description, end_time, total_paused_ms, error, is_backgrounded}`. `task_notification` carries `status: completed|failed|stopped`, `output_file`, `summary`, `usage` and `resource_links`. `background_tasks_changed` (v2.1.203+) is the full live set; the docs say to replace any cached set on each payload, and a repeated `initialize` triggers a snapshot. — [TS reference](https://code.claude.com/docs/en/agent-sdk/typescript#sdkbackgroundtaskschangedmessage)
- `stopTask(taskId)` / `stop_task`: a `task_notification` with `stopped` follows. Since 0.3.163 it returns success when the task is already gone. `backgroundTasks(toolUseId?)` / `background_tasks` moves foreground Bash commands or subagents to the background (Ctrl+B) and rejects if background tasks are disabled. — [TS reference](https://code.claude.com/docs/en/agent-sdk/typescript#backgroundtasks); [Python reference](https://code.claude.com/docs/en/agent-sdk/python); [TS SDK CHANGELOG 0.3.163](https://github.com/anthropics/claude-agent-sdk-typescript/blob/main/CHANGELOG.md)
- `get_task_output {task_id}` returns `{output, total_bytes, truncated}`, the last 8 KiB of a shell or Monitor task's output ("a host polls it while the task runs"). It is in the public types, but there is no Query method and no docs page. — [sdk.d.ts 0.3.312](https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk?activeTab=code)
- `perTaskStopAffordance` (initialize; SDK option since 0.3.246) declares that the host renders per-task stop buttons. Then an interrupt in an open-input session aborts only the turn and spares background agents and workflows. Without the declaration, an interrupt kills them. With a one-shot `-p` run (stdin closed), they are killed at the held-result release regardless. ## 4. Sessions: resume/continue/session-id/fork, storage, rewind/checkpoints, compaction; how SDK hosts do branch/edit/rewind

### Takeaway
Sessions persist as JSONL under `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl` unless `--no-session-persistence` is set (machdoch sets it today, which disables resume, fork and rewind). The building blocks:
- Start: `--session-id <uuid>`.
- Resume: `--resume <id|name|path>`, `--continue`.
- Branch: `--fork-session`.
- Truncate at a message: `--resume-session-at <msg-uuid>` (+ `--resume-drops-turn`).
- File rewind: `rewind_files` (needs `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=true` and `--replay-user-messages` for UUIDs).
- Compaction is reported via `compact_boundary` and `status: compacting`.
- Library-level helpers (`listSessions`, `getSessionMessages`, `forkSession({upToMessageId})`, `renameSession`, `tagSession`) exist only in the SDK.

### Cited Findings

## 5. Permissions & user input: canUseTool / can_use_tool, permission-prompt tool, permission modes, AskUserQuestion, elicitation, request_user_dialog, hooks

### Takeaway
Approvals and clarifying questions reach a host as `can_use_tool` control requests when the CLI runs with `--permission-prompt-tool stdio` (what the SDK passes for `canUseTool`) over stream-json. `AskUserQuestion` always falls through to this callback, even in `bypassPermissions` or with allow rules. That is why machdoch, which bypasses permissions with no prompt host, gets no usable questions today. The modes are `default` (shown as "Manual"), `acceptEdits`, `plan`, `auto`, `dontAsk` and `bypassPermissions`. `--permission-prompts none` (v2.1.259) auto-denies for unattended runs. MCP elicitations arrive as `elicitation` control requests. Tool-driven dialogs arrive as `request_user_dialog`, opt-in via `supportedDialogKinds` (public type, undocumented). Hooks can be registered as host callbacks via `initialize.hooks` → `hook_callback`.

### Cited Findings
- Evaluation order: hooks, then deny rules (deny even in bypass), then ask rules (fall through to `canUseTool` even in bypass), then the permission mode, then allow rules, then `canUseTool`. "`AskUserQuestion` and MCP tools whose server sets `_meta[\"anthropic/requiresUserInteraction\"]` always fall through to the callback, even when an allow rule matches. In `dontAsk` mode both cases are denied." In `bypassPermissions`, everything reaching the mode step is approved, except critical-path removals and flagged dangerous `rm`. The SDK passes the special value `--permission-prompt-tool=stdio` and refuses to combine `canUseTool` with `permissionPromptToolName`. — [CLI reference](https://code.claude.com/docs/en/cli-reference); [sdk.mjs 0.3.312](https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk?activeTab=code)

### Inferences

## 7. Plan, diff and progress UX: task lists, plan mode, file diffs, partial messages, subagent text, progress summaries

### Takeaway
Most of the progress UX is available in stream-json:
- Live text and thinking deltas via `--include-partial-messages` (`stream_event`).
- Subagent transcripts via `--forward-subagent-text` (2.1.211).
- One-line subagent progress via `agentProgressSummaries` (initialize; `task_progress.summary`).
- Structured diffs via `tool_use_result` (Edit/Write `structuredPatch`).
- Plans via `ExitPlanMode` output.

Caveat: the TodoWrite/Task list tools are not provided by default on the newer models machdoch uses (Opus 5.x etc.) unless the host opts in.

### Cited Findings
- `--include-partial-messages` emits `stream_event` lines (`text_delta`, etc.) and needs `-p` plus stream-json. With a gateway, `ping` events act as liveness signals. Since 0.3.290, interrupted streams get a closing `message_stop`. — [Headless, Stream responses](https://code.claude.com/docs/en/headless); [TS reference, Options](https://code.claude.com/docs/en/agent-sdk/typescript#options); [TS SDK CHANGELOG 0.3.290](https://github.com/anthropics/claude-agent-sdk-typescript/blob/main/CHANGELOG.md)
- Subagent messages carry `parent_tool_use_id`. By default only their tool_use/tool_result blocks stream. `--forward-subagent-text` / `CLAUDE_CODE_FORWARD_SUBAGENT_TEXT` also forwards text and thinking at every nesting depth (flag added in 2.1.211; nested in 2.1.219; forked skills in 2.1.265/2.1.275/2.1.287). — [Headless, Follow subagent messages](https://code.claude.com/docs/en/headless); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

### Inferences
- With Opus 5/Fable 5/Sonnet 5 models, machdoch's planned "task list" UI will stay empty unless it sets `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` (env on spawn) or adds `TaskCreate` to `--allowedTools`. The docs note that newer models deliberately skip the checklist, so this costs context.

- None material beyond the `get_plan` semantics (internal).

## 8. Other: fast mode, structured output, budget, fallback model, plugins/skills/agents/output styles, MCP via SDK, `/goal`, remote control

### Takeaway
Fast mode in SDK and `-p` sessions is per-session opt-in. Pass `fastMode: true` through the settings layer: `--settings '{"fastMode":true}'` at launch, or `apply_flag_settings {settings:{fastMode:true}}` mid-session. That is exactly what `fast_mode_disabled_reason: "sdk_opt_in_required"` means. Structured output (`--json-schema` → `result.structured_output`), budgets (`--max-budget-usd`), fallback chains (`--fallback-model a,b`), custom agents (`--agents`), plugins, skills, output styles, in-process MCP (via `sdkMcpServers` + `mcp_message`) and `/goal` (works in `-p`) are all usable from a raw CLI host. Remote Control is an interactive-session feature; its SDK control request is internal.

### Cited Findings
- Fast mode reason code `sdk_opt_in_required`: "The session hasn't opted in to fast mode: pass `fastMode: true` in the `settings` option or through `applyFlagSettings()`". Other codes: `free`, `preference`, `extra_usage_disabled`, `network_error`, `unknown`, `not_first_party`, `disabled_by_env`, `model_not_allowed`, `pending`. The same pair of fields appears on `system/init`, the `initialize` response and the `result` (v2.1.219+). — [TS reference, SDKResultMessage](https://code.claude.com/docs/en/agent-sdk/typescript#sdkresultmessage)
- In `-p`, "`/fast` works only in a session launched with fast mode in its `--settings` value, for example `claude -p --settings '{"fastMode": true}'`; the toggle then applies to that session only and isn't saved as your default" (v2.1.205+). Managed `fastModePerSessionOptIn: true` refuses `/fast on` outside interactive terminals. `ModelInfo.supportsFastMode` exists (0.2.69). Results report `usage.speed` (`standard`/fast). — [Fast mode](https://code.claude.com/docs/en/fast-mode); [TS SDK CHANGELOG 0.2.69](https://github.com/anthropics/claude-agent-sdk-typescript/blob/main/CHANGELOG.md); [local suggest.jsonl](file:///C:/Users/ehrha/AppData/Local/Temp/claude/C--Development-machdoch/dd3e5508-041e-4930-b633-c0e644aa1f2e/scratchpad/suggest.jsonl)

### Gaps
