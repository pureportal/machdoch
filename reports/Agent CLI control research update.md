# Fix goal verification before adding more agents

machdoch's most valuable next features are not more agents or more protocol wiring, but a control layer that can tell whether work actually finished: evidence-labelled goal verdicts, a structured Blocked state, a constraint ledger that survives compaction, and budgets that reflect cost rather than raw token counts. These rank first because they are cheap and because the local record is blunt: **of 45 goal records on one machine, 1 is complete, none of the 35 native ones is, and 17 end with "could not be verified"**. Version 37.3.2 already ships a control channel that lasts one turn on all three CLIs, with steering, questions, plans, usage and per-task stop, so none of that needs recommending again. **Nothing outlives the turn**, which makes durable provider sessions the largest remaining bet: every CLI supports them, and they unlock resume, fork, rewind and background work that survives the turn. For the two headline asks, follow-up prompts have a new native route on Codex (`thread/sample`, 0.164.0 and later) but the weakest evidence of anything here, so they should appear only at boundaries, be grounded in verified state, and ship with a holdout. Background tasks are killed about ten seconds after a result on every provider, and fixing that is a host change more than a CLI gap. The newest papers push the same way: default to one agent, verify outside the transcript, and do not ship learned kill-and-restart. Nothing here was run live: CLI and API capabilities come from documentation and source, most paper figures are abstract-level from unreplicated preprints, and value and effort labels are my judgment.

## machdoch 37.3.2 steers one turn well and forgets everything after it

The live control surface is real and recent. Reading the working tree at 37.3.2 (HEAD `f5f09c47`, with uncommitted edits present, so line numbers drift) shows steer, question cards, plan display, task lists, per-task stop on Claude and Copilot, usage and limit meters, Claude and Codex fast mode, and Codex review on all three "live session" transports, in `apps/client/src/core/_helpers/claude-interactive-session.ts`, `codex-app-server-session.ts` and `copilot-server-session.ts`. Those transports only run when `agentFeatures.liveControl` is set, and only desktop chat submission sets it (`apps/client/src/tauri/ui/chat-session/_helpers/use-session-task-submission.ts:562-567`). Native goals, scoped workers, read-only validators, Ralph blocks and scheduled runs fall back to paths with no steering. Follow-up suggestions ship for every provider, but through the weakest route: a system-prompt instruction and a trailing `<machdoch-follow-ups>` block (`apps/client/src/core/_helpers/follow-up-suggestions.ts`), with Claude's native event on top. Uncommitted edits add automatic continuation after Claude's `--max-turns` inside one process, which at default limits allows about 64 x 17 = 1,088 model turns before a stop.

**Resume, fork, rewind and compaction control are absent on every path.** `--no-session-persistence` is unconditional, provider homes live in a temp root that is disposed at the end (`apps/client/src/core/provider-enrollment/materializer.ts`), Copilot sends `session.destroy` at turn end, and `EXTERNAL_AGENT_COMPLETION_SHUTDOWN_GRACE_MS` (10,000) in `apps/client/src/core/_helpers/external-agent-provider.ts` still ends background work after a result. Remote users can see live state, answer questions and cancel the whole task, but `steer` and `stop-task` do not exist as fleet commands (`packages/fleet-protocol/src/index.ts`), and the control endpoint is loopback only. Native goals have no live state at all. Rate-limit data produces notices, but nothing in `goals/` or `ralph.ts` reads it, so a goal cannot wait for a window reset. Multi-part questions answered through a chat message receive the same text for every item (`apps/client/src/tauri/ui/chat-session/_helpers/session-needs-input.ts`). The host layer around this is substantial: goal mode, RALPH flows with checkpoints and leases, parallel workers, an adaptive controller, a reasoning bank, memory, a scheduler and fleet commands. But it treats each provider run as disposable and carries context as prompt text. Ralph alone has durable checkpoints and resume.

### Local goal records show long, expensive runs that rarely finish

This is the only measured data from machdoch itself. It comes from goal status files on one machine, read for numeric fields and fixed system reason strings.

| Mode, status | n | Median tokens (M) | Median turns | Median elapsed (min) |
|---|---|---|---|---|
| machdoch, active | 3 | 123.9 | 10 | 890 |
| machdoch, blocked | 6 | 63.4 | 5 | 475 |
| machdoch, complete | 1 | 11.1 | 4 | 126 |
| native, active | 13 | 3.9 | 2 | 887 |
| native, blocked | 3 | 79.4 | 2 | 1,214 |
| native, paused | 19 | 92.8 | 1 | 288 |

About 3,423M tokens are recorded across the 45 files, and **no record set a time, token or turn budget**. Fixed reason strings include 17 x "The goal could not be verified. Resume to continue." and 2 x verification timed out after native runs of 188M and 330M tokens. Eight "parallel worker failed" records predate fix commit `11daaaa6` and may already be resolved. Sixteen records are `active`, most with an empty reason, and four sit within 886-890 minutes on the same date, so most are probably crash or kill leftovers, though the data cannot separate runs still in progress. The sample includes development and test runs, goal records do not name the provider, and elapsed time is wall clock and may include sleep. It supports a structural inference rather than a rate: a native goal gets one evaluator pass over truncated evidence (`apps/client/src/core/goals/goal-evaluation.ts`) and then pauses unless complete (`apps/client/src/core/goals/run-goal.ts`), and resume starts a fresh process that re-pays context.

Token accounting makes the numbers look worse than the bills. `totalTokens` adds cache creation and cache reads at full weight (`packages/model-runtime/src/providers/stream-events.ts:218-232`), and usage reaches the goal only when a CLI run ends, so a killed run reports none. Goal records hold only totals, so the claim that a 10M run is mostly cache reads cannot be checked from them. The arithmetic shows why it matters: 9.9M tokens of reads on Opus 5.5 cost $1.98 at list price against $39.60 uncached ([prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)), and if the other 0.3M of a 10.2M run were all output, reads would be only 25% of the bill. **A token budget built on this total would trip far earlier than cost justifies.**

### One note's explanation of Claude's `error_max_turns` does not fit the native-goal path

The Claude research explains `error_max_turns` during `/goal` from the local `claude.exe` 2.1.312 bundle: the Stop-hook branch checks `--max-turns` before the block cap, and goal iterations share one prompt's turn count (an internal finding, not run). That mechanism is plausible, but machdoch's native-goal path does not pass the flag. `const maxTurns = nativeGoal ? undefined : getExecutorTurnLimit(config)` is present in `external-agent-provider.ts` at HEAD and in the working tree, with a comment saying a cap would cut the goal off. So the mechanism applies only where a `/goal` enters a capped run, such as text typed into a normal chat, and that path's continuation limit comes from `autopilotExecutorIterations` rather than the session's default of 0. This correction comes from reading code, and which path produced any given `error_max_turns` needs a run log.

### Evidence argues against several attractive features

| Do not build yet | Why |
|---|---|
| Learned kill-and-restart in the goal loop | Largest study found within-task AUC of about 0.50, and continuation won in 216 of 224 budget configurations ([Continue or Restart](https://arxiv.org/abs/2610.35971), preprint) |
| Generated repository overview files | No general success gain and over 20% higher cost ([Gloaguen](https://arxiv.org/abs/2602.11988), preprint); no measurable correctness change in 288 runs ([Khatri](https://arxiv.org/abs/2607.27250), preprint) |
| Custom compaction summarizer | No method beat default self-summarization across five strategies ([Salle](https://arxiv.org/abs/2610.31778), preprint) |
| Per-step learned model router | A CLI host mostly cannot switch per step, and in the best ablation the handoff, not the router, carried the result ([Scrouting](https://arxiv.org/abs/2608.04804), preprint) |
| Agent-to-agent chat as coordination, or "teams" | Native teams do not spawn under `-p` or the SDK ([Agent teams](https://code.claude.com/docs/en/agent-teams)), and paired agents succeed about 30% less often than solo ones ([CooperBench](https://arxiv.org/abs/2601.13295), preprint) |
| Darwin-style self-modifying archive | Outer-loop cost is high and unmeasured in what was read, and rewards must be reliable; an offline tuner with human approval is the feasible subset |
| Codex dynamic-tool swapping, host-reserved children, automation registration | Rust core or app-only in 0.166.0, with no JSON-RPC method ([PR #57553](https://github.com/openai/codex/pull/57553), [PR #57586](https://github.com/openai/codex/pull/57586), [scheduled tasks](https://learn.chatgpt.com/docs/automations.md?surface=app)) |
| Codex `personality`, `thread/prediction/*` | `personality` is dead ([config reference](https://learn.chatgpt.com/docs/config-file/config-reference)); prediction semantics are undocumented, and reading it as next-input prediction is a guess from its name |
| MCP Sampling and Roots | Deprecated in revision 2026-07-28, with a twelve-month minimum window ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) |
| Forced agent-first default view, custom merge queue, Gas Town-scale swarms | Anecdotal backlash on Cursor ([forum](https://forum.cursor.com/t/agents-window-feedback/160057)); GitHub already provides merge queues and the design is disputed ([Danjou](https://julien.danjou.info/blog/steve-yegge-deleted-the-wrong-thing), who sells merge queues) |

### A cheap version floor comes first, because behaviour has already moved

Three upgrade reasons are concrete. Claude Code 2.1.314 fixes `claude -p` exiting 0 with no output on a startup failure and closes a case where an excluded settings file could still supply saved settings, which machdoch's instruction isolation depends on ([changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). Codex 0.166.0 cut the default thread unload delay **from 30 minutes to 60 seconds** ([PR #57242](https://github.com/openai/codex/pull/57242)) while the [app-server docs](https://learn.chatgpt.com/docs/app-server) still said 30 minutes on 2026-10-30, and removed `detached` from `review/start`, which should not break machdoch because its call omits delivery. Copilot 1.0.104 made SDK Autopilot wait for attached background tasks while `-p --autopilot` keeps its timeout ([changelog](https://raw.githubusercontent.com/github/copilot-cli/main/changelog.md)). machdoch meanwhile moved runtime skew out of sight. It hand-writes the Copilot protocol with only a `--server` probe as a gate, and sends Claude's `cancel_queued` and `priority` without a version check. The only version check seen is for native goals. Probing the version, treating "unknown method" as feature-absent, and offering an update prompt is the fix, and every new Codex method above needs it, since those methods are absent from the installed 0.159.1 schema. Watch one upcoming change closely: `--bare` "will become the default for `-p` in a future release" and turns off background commands and subagents ([Headless](https://code.claude.com/docs/en/headless)). machdoch already adds `--bare` when an API key is present (`apps/client/src/core/provider-enrollment/materializer.ts`, `canUseClaudeBareMode`) and strips it only for native goals, so **by the docs, API-key Claude runs and subscription Claude runs have different background capabilities today**. That reading has not been run.

### Durable sessions are three different migrations with one supervisor

The shared design is one long-lived Claude process per active chat, one Codex app-server multiplexing threads, one Copilot client multiplexing sessions, with idle eviction and resume by id. Ralph's checkpoints, 2-minute leases and heartbeat are the existing precedent in `apps/client/src/core/ralph.ts`, and a "goal as durable run" could reuse them instead of starting fresh, which is my inference.

On Claude, dropping `--no-session-persistence` and keeping stdin open past `result` gives resumable sessions. Interruption should use `interrupt` or SIGINT, because SIGTERM leaves the turn unfinished with no result ([Headless](https://code.claude.com/docs/en/headless)). `CLAUDE_CODE_RESUME_PROMPT` overrides the continuation text ([env vars](https://code.claude.com/docs/en/env-vars)). Compaction-and-resume fixes in recent versions apply only to "compactions from this version on" ([changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)), which argues for a floor. The default system prompt snapshot means an updated machdoch instruction does not reach an existing session (local `claude --help`, 2.1.312). The Rust host cannot use the SDK-only session store, so tailing JSONL is the equivalent.

On Codex, a persistent `CODEX_HOME` is required, and `config.thread_unload_delay_secs` should be set explicitly given the new 60-second default. Goal continuation fires on thread idle and restores on resume ([extension.rs](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/ext/goal/src/extension.rs)), so a goal thread must stay subscribed. Avoid two app-servers on one home while a goal runs: older versions double-ran, and the claim that 0.163.0 returns a conflict rests on one community reproduction with no maintainer confirmation ([issue #32793](https://github.com/openai/codex/issues/32793)).

On Copilot, replace `session.destroy` with `session.detach`, which SDK v1.0.13 introduced so that disconnecting does not end a shared session ([SDK changelog](https://raw.githubusercontent.com/github/copilot-sdk/main/CHANGELOG.md)), then call `session.resume`.

Papers add a requirement the protocols do not: **restoring is not recovering**. A TLA+ and fault-harness study found LangGraph 1.2.9 re-executing completed work after SIGKILL and pydantic-graph 1.x unable to resume after a mid-node crash, and it offers six testable properties ([Resume Means Resume](https://arxiv.org/abs/2608.03836), preprint, abstract-level, single author, re-check framework claims). A second paper shows a restored checkpoint can resume a state that never coexisted with its external effects ([Safe to Resume?](https://arxiv.org/abs/2608.29381), preprint). So machdoch should treat restore as a verification event: re-check the working tree against the checkpoint, invalidate earlier verification results, and run the six properties as a kill-at-every-step suite against RALPH first, since it already persists state.

The evidence is weak and mostly indirect. Live A/B tests raised click-through by 34% in query suggestion ([Yin et al.](https://arxiv.org/abs/2508.15811), accepted at KDD 26), but clicks are not value and the setting is not coding. The most applicable result is about timing rather than prompts: in a five-day field study of 15 developers, workflow-boundary suggestions got 52% engagement, while mid-task ones were dismissed 62% of the time ([Kuo et al.](https://arxiv.org/abs/2601.10253), IUI'26). Next-step prediction remains poor on real behaviour, with best Pass@1 of 13.57% for a plain LLM and 35.57% for an agent needing about 23 tool interactions per prediction, across 1,246 developers ([ProCodeBench](https://arxiv.org/abs/2605.05700), preprint, full text partly read). **I found no randomized study of follow-up suggestions in coding agents**, and none testing whether one-click next steps deepen over-reliance, although low-effort use correlated with lower comprehension in a 54-student study ([Balepur et al.](https://arxiv.org/abs/2607.26375), in-progress preprint).

So the recommendation has a narrow shape. Generate the first candidates from verified state at no model cost ("tests in X never ran", "goal check still failing", "blocker cleared"), which no study tests directly but which is defensible by construction. Use native or side-call generation as a second layer, and retire the prompt block on providers that have a side call. Show them only at turn or commit boundaries, suppress them after a rejection or error, and copy Claude's backoff after repeated ignores. Keep a holdout and judge success on downstream outcomes such as later correction count and goal verdict, not on clicks.

### Background work needs a stop policy before it needs a tray

Claude has four separate lifecycles: in-session tasks over stream-json, local background sessions through shell commands, cloud sessions, and scheduled tasks. Only the first can be embedded, because `--bg` rejects `-p` ([Agent view](https://code.claude.com/docs/en/agent-view)). The in-session route is therefore the real integration, and the Stop hook input distinguishes "done" from "paused waiting" through `background_tasks[]` and `session_crons[]` ([sdk.d.ts](https://unpkg.com/@anthropic-ai/claude-agent-sdk@0.3.314/sdk.d.ts)). Copilot's task API is the richest of the three on paper, including steering a background agent with `sendMessage`, and Codex lists terminals with `processId`, `command`, `cwd`, `osPid`, `cpuPercent` and `rssKb` ([app-server docs](https://learn.chatgpt.com/docs/app-server)), but only behind `experimentalApi`, which machdoch already declares.

The order of work follows from that. First, replace the fixed post-result grace with each provider's own exit logic whenever tasks are live, and keep the existing panel visible until they end. Second, implement three explicit stops: stop turn that spares background work (Claude `interrupt` with `perTaskStopAffordance` declared ([SDK changelog 0.3.246](https://github.com/anthropics/claude-agent-sdk-typescript/blob/main/CHANGELOG.md)), Copilot `interruptMainTurn`, Codex `turn/interrupt`), stop task (add Codex `backgroundTerminals/terminate`), and close session. Third, once sessions persist, handle turns the user did not start, and show "waiting on background work" for a goal, because in `-p` the goal evaluator is skipped while background work runs and check-ins arrive only at turn end ([Goal](https://code.claude.com/docs/en/goal)). A thin local "send away" action can come at any point: `claude --bg --name X "<prompt>"`, poll `claude agents --json --all`, read `waitingFor`, and offer an attach terminal when blocked, since dialogs cannot be answered by a peek reply and no `claude send` exists. One trap: when a `-p` run ends, MCP tasks continue on the server, and an automatically backgrounded call loses its result ([Headless](https://code.claude.com/docs/en/headless)), so machdoch's MCP servers should not depend on task `input_required` under `-p`, where it is cancelled ([MCP](https://code.claude.com/docs/en/mcp)).

### Native goals should report to machdoch's verdict rather than replace it

Claude's `/goal` is a session-scoped prompt Stop hook on the small fast model. It calls no tools and "can only judge what Claude surfaced" ([Goal](https://code.claude.com/docs/en/goal)). An open issue reproduced on 2.1.308 on Windows 11 reports the hook firing 74 times and blocking 73, with 55 reasons quoting the user's stop messages and still ruling "not met" ([issue #101528](https://github.com/anthropics/claude-code/issues/101528), one reporter, no maintainer response). In the local 2.1.312 bundle the block cap returns `reason:"completed"`, so a successful-looking `result` cannot prove the goal finished, and the `active_goal` state event was found queued only behind `CLAUDE_CODE_REMOTE`, so a local host may never see it. Both are internal findings, not run. A host-owned Stop hook callback is the realistic alternative: it can run tests and read git status, honor a user stop, and set `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` ([hooks guide](https://code.claude.com/docs/en/hooks-guide)). Whether `--settings` hooks fire under `--setting-sources ""` and under `--bare` is untested, so prefer `initialize.hooks` where a control channel exists.

Codex's goal source now shows the continuation rules. Continuation fires on idle. The runtime sets `blocked` on turn errors and after three consecutive empty or failed turns, `usageLimited` on limit errors, and `budgetLimited` when the token budget runs out, and the model can set `complete`, `blocked` after a three-turn audit, or `paused` on request ([tool.rs](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/ext/goal/src/tool.rs), [runtime.rs](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/ext/goal/src/runtime.rs)). machdoch should send `origin: "user"` from 0.166.0 ("Missing provenance does not supply user authorization"), although what it gates and whether 0.159.1 rejects it are untested. It should also stop rejecting budgets for native goals (`apps/client/src/core/goals/goal-execution.ts:178-182`), since Codex has a native token budget, though whether that budget counts cached tokens is undocumented. And it should render `blocked` as resumable. Plan-mode turns do not advance a goal, so an active goal parked in Plan mode will look stalled.

### ACP is for breadth, and the other standards are design references

ACP v1 is stable and v2 is still a draft to gate behind flags ([v2 announcement](https://agentclientprotocol.com/announcements/acp-v2-draft.md)). Native drivers should stay for the three main CLIs because steering, quota, the editable queue and fleet remain outside stable ACP. An ACP client is the right path for additional CLIs, with Cursor ([docs](https://cursor.com/docs/cli/acp)) and OpenCode ([docs](https://opencode.ai/docs/acp/)) first, Qwen Code as a cheap add-on, Gemini CLI only for paid and enterprise users since the docs say it "was replaced by Antigravity CLI" for others ([Gemini docs](https://geminicli.com/docs/cli/acp-mode/)), and Aider not at all. The active drafts are worth copying now: the Background Work RFD (a `background` list on state updates, per-item cancel, and `session/cancel` stopping only foreground work) ([RFD](https://agentclientprotocol.com/rfds/v2/background-work)) already resembles `AgentLiveTracker`. machdoch's live state is a snapshot with no `running`/`requires_action`/`idle` lifecycle or stop reason today, so adding those fields pays off regardless. Microsoft's AHP, with snapshots plus ordered actions and replay on reconnect, fits a multi-client relay well but is young, so read it as a design reference ([VS Code blog](https://code.visualstudio.com/blogs/2026/08/26/agent-host-architecture)). A2A and AG-UI have no in-scope CLI behind them. MCP 2026-07-28 is final and breaking: stateless, with no `initialize`, so machdoch's host needs a dual-version client that probes `server/discover`, treats a missing `resultType` as complete, and persists task IDs so polling survives a crash ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [Tasks](https://modelcontextprotocol.io/extensions/tasks/overview)). Whether `@modelcontextprotocol/sdk` 1.32.2 already handles this was not verified.

## Papers favour checking and constraint-keeping over more agents

Almost all of this literature is under a year old, much of it weeks old. Each figure below is abstract-level unless marked otherwise, read through a summarizing fetch tool, and should be checked against the PDF before public quotation. The status tags matter: "preprint" means no venue was listed.

### Goal verification is the strongest and most usable area

A preregistered pilot varied only the evaluator controlling a loop, against an isolated oracle. Across 54 cycles the agent claimed improvement every time while 56% showed zero or negative change, the strongest in-transcript judge accepted real regressions 44% of the time, and bare accept-or-reject nearly matched full feedback (110.0 against 113.0). The problem vanished when success was checkable from the artifact ([Park & Choi](https://arxiv.org/abs/2607.25152), preprint pilot). A preregistered study with 46 seeded faults found a fresh-context verifier beat the builder's tests (Holm p = 0.006), while **a different-provider verifier added no detection** ([Sion & April](https://arxiv.org/abs/2610.28667), preprint, small). A review of shipped loops found 47 vacuous gates across 69, and zero false accepts on 209 mutants turned into 23.3% on a new mutant family ([Bhardwaj et al.](https://arxiv.org/abs/2609.27871), preprint). Across 17 models, cumulative evasion over five rounds was 40.5% with detailed feedback against 20.3% with generic rejection, though that comparison also varied history and does not isolate explanations ([Huang et al.](https://arxiv.org/abs/2609.28614), preprint). Visible tests overstate success as code grows, by a gap of 28 points per tenfold code-size increase across 30 tasks ([SpecBench](https://arxiv.org/abs/2605.21384), preprint).

machdoch's separate evaluator is directionally right, but "separate model call" is not the property that matters. The evaluator uses the same provider and model with up to 12 x 4k of history, 20k of response and 10 x 4k evidence sections, and has a 5-minute cap (`apps/client/src/core/goals/goal-evaluation.ts`). The build is concrete. Classify each goal as artifact-checkable or external, and require a command, URL or metric for external ones. Tag each verdict as harness-observed, artifact-checked or transcript-only. Lint goals for vacuity ("passes because nothing ran") and self-attestation ("the agent supplies the number"). Keep acceptance checks and oracles outside the agent-readable tree, because agents sought hidden grading files unprompted in about 80% of a 244-run sealed replication ([When Agents Coordinate](https://arxiv.org/abs/2608.16801), preprint). Send the worker a coarse verdict and keep the rationale for the user. Treat "this is impossible" as a claim that triggers review, since falsely reporting infeasibility was a common failure over 20 long tasks ([SWE-Marathon](https://arxiv.org/abs/2606.07682), preprint). Do not sell cross-provider evaluation as extra rigour without further evidence, even though a multi-CLI host is well placed to offer it. A "Dispute verdict" action captures false negatives, which exist too: human review recovered 5.45 to 8.49 points an automatic evaluator missed on web tasks ([Gan et al.](https://arxiv.org/abs/2610.01491), NeurIPS 2026 workshop poster).

A required Blocked ticket has the largest sample behind it. Across 8 models and 19,371 trajectories with injected blockers, almost all runs had enough evidence to ask, yet a third exhausted the budget. An `escalate_to_human` tool cut exhaustion **from 34.0% to 6.7%**, and a rule-based monitor tested on one model raised post-restore success from 7.6% to 21.8% ([Chen et al.](https://arxiv.org/abs/2610.31895), preprint posted days before these notes, full text partly read). Two costs are measured too: progress was incomplete in 35.7% of 3,149 tickets, and premature handoffs dropped one model's recoverable-fault success from 70.1% to 63.7%. So the ticket needs required fields (what broke, saved changes, remaining work, what was verified and not, help needed, resume condition) and should fire on stated patterns rather than on any error. Goal mode's existing `blocked` status is the natural home.

### Compaction loses behaviour rather than task, which a host can fix cheaply

Two independent studies agree on the failure. An agent deleted emails without approval in 30 of 100 sessions after compaction and in none before, compactors retained 17% of injected constraints, and an extractor that keeps constraints apart from the summary retained over 90% across three scenarios ([Wang et al.](https://arxiv.org/abs/2608.11242), preprint; extractor's sample not in the abstract). In a fixed OpenCode scaffold, no compaction method beat default self-summarization and threshold had no measurable effect on 1M-context models, yet the first summary dropped about one third of anticheating rules, and in real sessions how-to-work and do-not instructions were dropped about 6x more than build specifications ([Salle et al.](https://arxiv.org/abs/2610.31778), preprint). The second paper also warns that benchmarks understate losses because progress lives on disk. Claims for specific methods are contested and mostly self-reported ([Slipstream](https://arxiv.org/abs/2605.08580), [CliffCompaction](https://arxiv.org/abs/2609.26779), [AutoCompact](https://arxiv.org/abs/2610.02163)).

machdoch should therefore not write a summarizer. It should extract user prohibitions and approval rules into a host-owned ledger and re-inject them after every compaction and new session. That fits its prompt-carried architecture, and on Claude a PreCompact hook can add the ledger while PostCompact's `compact_summary` lets machdoch audit what was kept ([hooks](https://code.claude.com/docs/en/hooks), [sdk.d.ts](https://unpkg.com/@anthropic-ai/claude-agent-sdk@0.3.314/sdk.d.ts)). Compaction is invisible today except for a Copilot notice, so showing the event is the first step. Rules in the ledger should be written as prohibitions, based on one study of 5,000+ Claude Code runs that needs replication, and which also found random rules did as well as curated ones ([Guardrails Beat Guidance](https://arxiv.org/abs/2604.11088), preprint). Periodic re-injection matters more than file layout: 1,650 sessions found no effect from file size or position, but compliance odds fell about 5.6% per generated function ([McMillan](https://arxiv.org/abs/2605.10039), preprint, post hoc).

### Loop evidence is sobering, so measure before tuning RALPH

LoopsBench ran 112 long-horizon tasks as dependency graphs of testable units. Resolve rates were **Claude dynamic workflows 24.11%, Codex goal mode 20.59%, Claude Code goal mode 17.65%, and a Ralph loop 7.84%**, with regression events per run of 0.36, 0.34, 0.13 and 0.17 ([LoopsBench](https://arxiv.org/abs/2608.00267), preprint, full text partly read). It tested one Ralph implementation, not machdoch's RALPH flow engine, its abstract and Table 1 disagree on unit counts (5,300+ against 37,296), and the cost appendix was not read. Still, fresh context did not remove regressions, so explicit state tracking is what to build: a progress ledger that keeps completed units as regression checks, plus a session-start ritual of reading the log, smoke testing and then working ([Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), vendor, no numbers). The practical step is to run machdoch's goal loop and RALPH flows on LoopsBench's methodology before investing further.

Budget evidence is firmer. At the baseline's 75th percentile, a turn limit cut cost 24-68% with minimal solve-rate loss, and dynamic extra turns on demand saved another 12-24%, on SWE-bench with three older models ([Gao & Peng](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/208/More-with-Less-An-Empirical-Study-of-Turn-Control-Strategies-for-Efficient-Coding-Ag), ICSE 2026 main track; task counts not on the page). This is the one peer-reviewed main-track result with a direct machdoch translation. Learn percentiles per provider and task class from stored runs, add a reminder near the limit and an on-demand extension, and do not apply them to long multi-session goals without checking, since SWE-bench tasks are shorter. It runs against the current direction of travel: uncommitted edits remove the adaptive controller's executor caps, Codex and Copilot get no turn cap from machdoch, and Claude's continuation can reach about 1,088 turns. Stopping is contested. The largest study reports near-chance within-task prediction and that continuing beat restarting ([Continue or Restart](https://arxiv.org/abs/2610.35971), preprint, 147,002 traces), while a monitor saved 4.5% on SWE-bench Verified and up to 31% on a costlier subset ([StopLoss](https://arxiv.org/abs/2610.25525), preprint). A fail-fast design reached 71.8% against 66.8% for cold restart at a 25% false-positive target ([Wang et al.](https://arxiv.org/abs/2608.03222), preprint, one benchmark). Those are different targets and metrics, so hard budget stops are safe to build and automatic restart is not. A manual "Restart with what it learned" button that attaches the previous diff is the low-risk subset.

For routing, a cheap scout that explores and produces a handoff with sandbox-verified reproduction claims solved 159 of 266 tasks against the best single model's 158 at about one-fifth the cost per solve, and **always using the cheapest fixer with the handoff tied the router** ([Scrouting](https://arxiv.org/abs/2608.04804), preprint; authors built the searcher). That makes a scout stage a better first experiment than any router, and machdoch can express it as a read-only first step in a flow.

### Parallel agents must earn fan-out, and worktrees isolate bytes rather than compatibility

The best-controlled results point one way. STORM's own baselines show git-worktree multi-agent scoring below single-agent on Commit0 on all three models tested and single-agent having the best cost efficiency everywhere, though those baselines lose to the authors' own system and no repeat-run variance is reported ([STORM](https://arxiv.org/abs/2605.20563), preprint, full text read). Co-Coder reports up to +14.0% pass rate and 35% lower API cost with cohesion-aware partitioning over 28 tasks, against file-based parallel raising cost 44-60% for little gain and Claude Code Agent Teams being fastest but below sequential on quality ([Co-Coder](https://arxiv.org/abs/2606.00953), preprint, full text read, "up to" figures). Across 260 configurations, multi-agent ranged from +80.8% on decomposable finance to -70.0% on sequential planning ([Scaling Agent Systems](https://arxiv.org/abs/2512.08296), preprint, not coding-specific; use v3 figures). The strongest admission result gained reliability, not speed: pair pass rose from 23.3% to 50.0% with static intent admission, but 96.7% of executions were serialized, and dynamic fail-closed blocking fell to 22.2% ([Claim Plane](https://arxiv.org/abs/2608.00947), preprint, single author, one model pair).

Conflict evidence measures two different things. Textual conflicts are common, at 27.67% of 107K+ simulated agent PRs against their base ([AgenticFlict](https://arxiv.org/abs/2604.03551), accepted at AIware 2026 per arXiv) and 41.7% cross-agent against 19.8% same-agent on 747 replayed pairs ([Xu et al.](https://arxiv.org/abs/2607.04697), preprint), which is a direct warning for a multi-provider host. Semantic combination failures were 1 in 834 runs on mined Django PR pairs and 97% on constructed tasks, and a message describing the finished concurrent change recovered 82% of runs ([Passes Alone](https://arxiv.org/abs/2609.25396), EXPRESS 2026 workshop). The authors warn that constructed rates do not estimate real frequency, and reviewed PRs are already selected for compatibility, so real rates in unreviewed concurrent agent work are unknown.

machdoch's adaptive controller picks 2 or 3 workers from regex and length scoring (`apps/client/src/core/adaptive-controller.ts`), and parallel workers cannot be steered or stopped individually. The change: default to one agent, require a decomposability check before fan-out, isolate hub files to one owner, serialize overlaps, and report realized parallelism rather than implying a speedup. Run each patch and the merged result through tests and classify combination-only failures. Send a sibling notice when an interface lands. Be stricter when mixing providers in one repo. Verification and allocation belong at the center, because central verification helps while a named coordinator gave no reliable gain ([When Agents Coordinate](https://arxiv.org/abs/2608.16801), 1,902 runs plus a sealed replication). Keep the single-person case in view: ParallelPilot raised ticket throughput 63% on short tasks in a 16-person within-subjects study without improving perceived redirect success ([Long et al.](https://arxiv.org/abs/2609.33113), preprint), so dashboards alone are not enough, and the steering action needs its own design.

### Developers pay for misalignment through correction, which is machdoch's cheapest signal

In 16,118 pushback episodes across 20,574 sessions, shares were constraint violation 38.33%, misread intent 26.95%, inaccurate self-report 22.58% and faulty implementation 17.82%, and next-session misalignment probability was 0.519 after a misaligned session against 0.336 otherwise ([Tang et al.](https://arxiv.org/abs/2605.29442), preprint, full text partly read, opt-in sources, reuses SWE-chat data). Agent self-report is therefore a documented failure mode, which supports building progress displays and long-run recaps from harness events (tests run, files changed), with agent narrative as a labelled second layer. Failures also tend to start early and stay hidden: on 3,843 trajectories, most began in the first few steps ([Zhao et al.](https://arxiv.org/abs/2607.09510), preprint), so an "early assumptions" card earns more than end-of-run review. Correction events can be classified into those forms and offered as one-click "promote to a reusable instruction" ([Park et al.](https://arxiv.org/abs/2609.24234), qualitative, under review). Typed steering verbs (add, change, drop requirement) that restate the goal back are a reasonable design with only benchmark support ([InterruptBench](https://arxiv.org/abs/2604.00892), simulated, non-coding). SWE-chat's numbers should be used carefully, because its current abstract and v1 full text disagree on pushback, 50% against 39% ([SWE-chat](https://arxiv.org/abs/2604.20779), COLM 2026).

Plan approval draws far more real rejection than permission prompts: **plans rejected 39% against 3% for permissions**, and testers caught 143 of 1,053 planted bad commands (13.6%), falling from about 17% to about 5% after 50+ prompts ([Anthropic](https://claude.com/blog/auto-mode-default-in-claude-code), vendor data justifying a product default, not independently reproduced). A randomized study of 113 non-professionals found user-written policies blocked 20.1 points less than per-action review, and 114 of 140 rules were "ask" ([Yan](https://arxiv.org/abs/2608.27443), preprint, simulated setting), so "write your own rules" is not the fix for fatigue. Plan-first cards can use existing question UI: Copilot `requestExitPlanMode`, Claude `can_use_tool` on `ExitPlanMode` followed by `set_permission_mode` (the docs do not spell this sequence out for hosts), and Codex plan collaboration mode. A plan step is not free, though: planning gave stronger models mostly cost reduction rather than accuracy across 176 matched settings ([Fan et al.](https://arxiv.org/abs/2609.20804), preprint).

Question gating has early support. A separate underspecification detector reached 69.40% on underspecified SWE-bench with simulated users ([Edwards & Schuster](https://arxiv.org/abs/2603.26233), EMNLP 2026 camera-ready), and asking only when two plausible answers produce behaviorally different programs reported +13.88 macro F1 on the authors' own benchmark ([CONTRA](https://arxiv.org/abs/2610.01769), preprint). No controlled experiment with real developers varying when an agent asks has been found.

### Memory helps only when execution gates what gets written

The reasoning bank's risk has a main-track citation: agents copy what they retrieve, memories that look correct can still mislead, and later task evaluations can act as free quality labels ([Xiong et al.](https://aclanthology.org/2026.acl-long.27/), ACL 2026; no sample size in the abstract). Accurate memories dropped every framework below no-memory on trap tasks that were adversarial by design ([MemTrapBench](https://arxiv.org/abs/2608.20202), preprint), and unaided self-generated skills gave no average benefit in the first version of [SkillsBench](https://arxiv.org/abs/2602.12670v1) (cite as v1, since v4's abstract no longer states it). Gated curators report gains, such as +17.2 points on hard tasks with commit only after real execution shows no regression ([SkillGLoW](https://arxiv.org/abs/2609.02217), preprint, 12 of 12 runs positive). The upgrade is to label lessons by verifier outcome rather than self-judgment, keep them itemized with merge operations, add a dead-ends store, gate consolidated lessons by replay, demote those correlated with later failures, and frame injected lessons as hypotheses to check. The current bank has helpful and harmful counts already (`apps/client/src/core/reasoning-bank.ts`), so this builds on the existing model. No study measures a learned lessons store in a real multi-week coding deployment with a control arm.

## Competing hosts set a remote and review baseline, with convergence rather than usage data

Remote control is the clearest gap. Conductor 0.92 (2026-10-23, Experimental) lets iOS users create workspaces, read chats, send messages, pick models and stop agents, with QR pairing ([changelog](https://www.conductor.build/changelog/0.92.0-remote-control)). Codex mobile covers tasks, instructions, approval and diffs ([docs](https://learn.chatgpt.com/docs/mobile)), and on 2026-10-22 added viewing and stopping background commands on remote hosts ([changelog](https://learn.chatgpt.com/docs/changelog)). Claude Code Remote Control uses outbound-only HTTPS, syncs subagent progress, reconnects after sleep, and pushes with presence detection ([docs](https://code.claude.com/docs/en/remote-control)). Cursor added local remote control on 2026-10-06 ([changelog](https://cursor.com/changelog/remote-control-local-agents)). No usage figures exist for any of these surfaces, so this rank rests on convergence, plus machdoch's confirmed gap. The fix is direct: add `steer`, `answer` and `stop-task` fleet commands, pass `onStopTask` to `AgentLiveRunDetails` in `packages/client-ui/src/conversation/remote-conversation-host.tsx`, and resolve an ambiguity in `apps/client/src/tauri/ui/chat-session/_helpers/use-chat-session-controller.ts`, where a fleet `submit-message` uses `input.runningAction ?? runningTaskMessageAction`. Whether a desktop steer preference can already apply to a remote message was not traced to a conclusion. Pairing and reconnection deserve tested flows, because forum complaints cluster there ([Codex thread](https://community.openai.com/t/codex-remote-from-mobile-endless-loop/1402800), search summary, anecdotal). Claude's Remote Control is subscription-only and off under some organization settings ([docs](https://code.claude.com/docs/en/remote-control)), so machdoch's relay can serve users it cannot.

The review loop is the second convergence. Claude Code desktop, Conductor and Devin all feed diff-line comments back to the agent ([desktop docs](https://code.claude.com/docs/en/desktop), [Conductor guide](https://conductor.build/docs/guides/review-and-merge), [Devin notes](https://docs.devin.ai/release-notes/overview)), and batching comments into one steering message works on all three CLIs without new provider support. CI and PR-comment repair exists as Claude Auto-fix and VS Code agent merge in preview ([roundup](https://github.blog/changelog/2026-10-01-github-copilot-in-vs-code-september-2026-releases)). The cheap transferable idea is to route a failing check back to the session that made the change, which machdoch's steer can already deliver. Codex's `review/start` also takes `baseBranch` and `commit`, while machdoch fixes the target to `uncommittedChanges` and triggers it only on an exact prompt match. Field evidence is thin but real: in a Meta rollout, a drift-from-request score gave 5.76 points extra drift reduction across 193 version pairs (one-sided p = 0.026, d = -0.28, Mann-Whitney p = 0.063), and 112 engineers gave 90.2% approval ([ARCTIC](https://arxiv.org/abs/2607.29516), preprint, full text partly read, self-selected, small effect). Automated review alone is no substitute: review-agent-only PRs merged at 45.20% against 68.37% for human-only, though selection confounds it ([Chowdhury et al.](https://arxiv.org/abs/2604.03196), MSR 2026). And reviewer load is the limit, with load per reviewer doubling across 196,212 PRs at one company ([He et al.](https://arxiv.org/abs/2607.01904), preprint), so a concurrency view paired with review capacity is more useful than a bigger board.

Automation is common but undifferentiated. Claude scheduled tasks are research preview and tied to one person's account ([docs](https://code.claude.com/docs/en/routines)), Conductor Routines are cloud only and hide routine workspaces from Home ([0.85.0](https://www.conductor.build/changelog/0.85.0-sections-routines-and-a-new-model-picker), [0.92.0](https://www.conductor.build/changelog/0.92.0-remote-control)), and Cursor's SDK channels wake agents on GitHub, Slack, webhook and cron events ([changelog](https://cursor.com/changelog)). machdoch's fleet can do something the cloud-first products do not emphasise: run a schedule on a chosen device, with its scheduler already in place. Its runs are unattended with no `liveControl`, so question handling must be decided before this grows, and Claude's host-declared scheduled run (`CLAUDE_CODE_HOST_SCHEDULED_RUN=1`) is unused ([TS reference](https://code.claude.com/docs/en/agent-sdk/typescript#declare-a-scheduled-run)). A cross-harness cost view is plausibly the best team differentiator, because each vendor dashboard covers mainly its own usage ([GitHub metrics API](https://github.blog/changelog/2026-08-07-copilot-usage-metrics-api-adds-agent-app-activity/)), though subscription plans limit what the CLIs expose. Best-of-N has shipped ([Cursor 3.0](https://cursor.com/changelog/3-0)), but no source measures whether it beats a single attempt at equal cost, so it should stay an explicit, cost-labelled action at N of 2 or 3.

## Conclusion

The integration question has changed character. The blocker used to be a missing control channel, and 37.2.0 built most of it. What the channel exposes now is a harder problem: **machdoch can steer an agent it cannot yet evaluate**. Better steering does not fix a verdict that reads only the transcript, and durable sessions would make things worse without verification, since longer runs and resumed state both widen the gap between what an agent claims and what is true. That is why verification should precede persistence, even though persistence is the larger capability gain. It also clarifies the ownership split: the CLIs own turns, compaction and their own loop mechanics, while machdoch owns the constraint ledger, the budget, the verdict and the record of what was observed. Native `/goal` and Codex goals are useful engines under that verdict, but not substitutes for it.

machdoch's less obvious asset is its data. The field's most trustworthy results came from paired designs and counterfactual replay on stored traces, and machdoch sees real runs across three CLIs on private repositories, which is exactly the population the literature lacks. Storing per-run cost categories, verdict classes, correction events and later outcomes would let it test turn budgets, stop policies, follow-ups and memory gates on its own traffic rather than inheriting benchmark numbers, and it would give a multi-CLI host something single-vendor products cannot produce: a like-for-like comparison of how each CLI behaves under the same control policy. The one caution from that same literature is that the comparison should not be sold as verification, because the only preregistered test of a cross-provider verifier found no added detection.
