# Persistent sessions unlock machdoch's deeper CLI integration

machdoch can ship almost every advanced feature on its list: steering, graceful interrupt, resume and fork, in-app questions, live plans and diffs, usage and rate-limit meters, review, fast mode and background-task control. **All three CLIs already expose these features over long-lived JSON protocols**: Claude Code's stream-json control protocol (the one the Agent SDK speaks), Codex's app-server JSON-RPC v2, and the Copilot SDK's JSON-RPC server. The CLIs are not what blocks them. machdoch's invocation model is. It starts a fresh process per turn, closes stdin after the prompt, disables persistence, has no host listening for the CLIs' questions, answers Codex server requests with -32601, and kills provider background processes about ten seconds after the result (machdoch source). The user's two examples get different answers. **Follow-up suggestions are native only in Claude Code** (`prompt_suggestion`). Its generator skips any conversation with fewer than two assistant messages, which explains machdoch's empty one-turn test. Codex and Copilot have no equivalent, so machdoch must generate suggestions itself. **Background tasks can be observed and stopped in all three CLIs**, but only while the process outlives the turn. The recommended protocol strategy is a hybrid: three native drivers feeding an internal event model shaped like ACP v2. ACP alone is not enough. It lacks rate limits, suggestions, standard steering, background-task control and review, and its Claude and Codex adapters wrap the same native protocols anyway. Stability differs sharply by vendor. Codex 0.159.1 marks nearly everything machdoch needs as stable in its generated schema. Claude documents the SDK behaviour but not the raw wire protocol. Copilot's GA SDK labels every generated RPC experimental, and machdoch pins a crate generated against a CLI 33 patch versions older than the installed one. That gives the build order: first show the data already arriving in today's streams, then open a control channel per CLI for each turn, then move to persistent provider sessions.

## A closed stdin and a handful of flags switch off most advanced features

Each per-turn invocation disables something specific. For Claude Code, `--no-session-persistence` means sessions "will not be saved to disk and cannot be resumed", which also rules out fork, truncate-and-resume and file rewind ([CLI reference](https://code.claude.com/docs/en/cli-reference)). Closing stdin after the prompt removes the input half of the control channel. The docs call streaming input the "preferred" mode: "a long lived process that takes in user input, handles interruptions, surfaces permission requests, and handles session management" ([Streaming Input](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode)). Model switching and runtime flag settings work "only in streaming input mode" ([TS reference](https://code.claude.com/docs/en/agent-sdk/typescript#query-object)). Without a prompt host, clarifying questions have nowhere to go, because **`AskUserQuestion` always falls through to the host callback, even in `bypassPermissions`** ([SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)). The ten-second kill also cuts across the CLI's own behaviour. Once stdin closes, `-p` waits up to ten idle minutes for background commands, subagents, Monitor watches and `/loop` wakeups, and can run follow-up turns when that work finishes ([Headless](https://code.claude.com/docs/en/headless)).

Codex loses features the same way. `codex exec --json` emits only thread, turn, item and error events ([Non-interactive docs](https://learn.chatgpt.com/docs/non-interactive-mode)), so there are no deltas, no live plan or diff, no rate limits and no steering. Threads persist as JSONL rollouts plus SQLite metadata under CODEX_HOME ([App-server docs](https://learn.chatgpt.com/docs/app-server)), so a per-run CODEX_HOME that gets deleted, plus `--ephemeral`, rules out resume. The goals path already runs the app-server. But it answers every server-initiated request with -32601, so any `requestUserInput` or MCP elicitation fails the run (machdoch source). machdoch's current settings do not stop those two request types from arriving.

Copilot has the same gaps. `--no-ask-user` matches the SDK rule that without a user-input handler "the `ask_user` tool is disabled" ([crate types.rs](file:///C:/Users/ehrha/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/github-copilot-sdk-1.0.7-preview.2/src/types.rs)). `--stream=off` suppresses message and reasoning deltas. Subagent events tagged with `agentId` are dropped. Usage is read from an OpenTelemetry file exporter, even though since CLI 1.0.81 `--usage-output-file` writes final usage JSON with per-agent metrics ([copilot-cli changelog](https://github.com/github/copilot-cli/blob/main/changelog.md)). Killing the process tree also kills attached shells that the CLI would otherwise keep alive.

None of these are CLI limits. All are host choices, and machdoch already has a foothold in each native protocol: it sends Claude's `initialize` control request for discovery, runs the Codex app-server for goals, and links the Copilot SDK for `models.list` (machdoch source). The more useful point is that **most of the missing features need a control channel that lives for one turn, not a session that lives indefinitely**. Steering, interrupt receipts, question cards, live deltas, plan and diff streams, usage pushes and background-task control all work within a single turn. Only resume, fork, warm-cache suggestions and background work that outlives a turn need persistent provider sessions. The roadmap below follows that split.

## The two headline asks: suggestions are Claude-only, background work needs a living process

### Follow-up suggestions are native in Claude and must be generated by machdoch elsewhere

Claude Code generates follow-up prompts natively. Two switches turn this on: the `--prompt-suggestions` flag, which requires `-p`, `--output-format stream-json` and `--verbose` (all of which machdoch already passes), or `promptSuggestions: true` on `initialize`. With either, the CLI emits `{type: "prompt_suggestion", suggestion, uuid, session_id}` after a turn's `result` ([CLI reference](https://code.claude.com/docs/en/cli-reference); [TS reference](https://code.claude.com/docs/en/agent-sdk/typescript#sdkpromptsuggestionmessage)). The message arrives after the result, so a host has to "iterate the stream to completion rather than breaking on the result" ([Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)). Each suggestion is "a short background request to the same model your session is using". It is mostly cache reads plus a few output tokens, and it counts toward plan limits ([Interactive mode](https://code.claude.com/docs/en/interactive-mode#prompt-suggestions)).

The generator has many skip conditions, and they explain machdoch's empty test. In the 2.1.312 bundle it skips with `early_conversation` when the transcript holds fewer than two assistant messages. It also skips on a cold or expired prompt-cache prefix, after an error, in plan mode, while a permission or elicitation is pending, when the rate-limit status is not `allowed`, after replies billed to usage credits, and for turns whose origin is scheduled, a task notification or host-synthetic ([local claude.exe bundle](file:///C:/Users/ehrha/.local/bin/claude.exe)). machdoch's Haiku test had one user turn and no tools, so the transcript held one assistant message. The run produced `assistant`, `rate_limit_event`, `post_turn_summary` and `result`, but no suggestion ([local test log](file:///C:/Users/ehrha/AppData/Local/Temp/claude/C--Development-machdoch/dd3e5508-041e-4930-b633-c0e644aa1f2e/scratchpad/suggest.jsonl)). These internal conditions can change without notice, but the documented summary agrees: "a single short `-p` query can emit none" ([Interactive mode](https://code.claude.com/docs/en/interactive-mode#prompt-suggestions)). Because machdoch re-sends history as prompt text, the CLI only ever sees one invocation's transcript. So **in today's architecture, suggestions can appear only on turns that made tool calls**, and only if machdoch reads stdout to the end instead of stopping at `result`. Reliable suggestions need the persistent sessions of Phase 2, where every human turn after the first qualifies and the cache stays warm. User messages should carry `origin: {kind: "human"}`, because the CLI treats unattributed messages as non-human for checks that need a typed prompt ([TS reference, SDKMessageOrigin](https://code.claude.com/docs/en/agent-sdk/typescript#sdkmessageorigin)).

Neither Codex nor Copilot has an after-turn suggestion feature. None of Codex's 83 notifications or its server requests carries one, and its config offers only recaps (`tui.auto_recap`) ([Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)). Copilot's events and RPCs show no suggestion primitive, either in the crate or on main ([SDK-main session_events.rs](https://github.com/github/copilot-sdk/blob/main/rust/src/generated/session_events.rs)). machdoch therefore has to generate them itself. For Codex, the cleanest route is a side call on an ephemeral fork: `thread/fork` with `ephemeral: true` (paginated threads also need `excludeTurns: true`), followed by a `turn/start` whose `outputSchema` returns an array of suggestions. That keeps the main thread's history clean and can use a cheaper model through fork overrides ([App-server docs](https://learn.chatgpt.com/docs/app-server)). Whether the fork reuses the prompt cache is unverified, so each suggestion should be budgeted as a full small turn. For Copilot, `session.ui.ephemeralQuery` "runs a transient no-tools model query against the current conversation context" and leaves history unchanged, though its request shape and billing were not checked ([crate rpc.rs](file:///C:/Users/ehrha/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/github-copilot-sdk-1.0.7-preview.2/src/generated/rpc.rs)). For any provider, machdoch's own API runtime already has a `followUps` field in its final-response schema (machdoch source), which makes it the natural fallback for every CLI. The weakest option is asking the main agent to put suggestions in its structured output: it works, but it pollutes the transcript and changes how answers render. Whatever the source, machdoch should copy Claude's skip rules: no suggestions after errors, in plan mode, near rate limits, or after repeated ignores. (Since 2.1.283, Claude shows suggestions less often after 20 unused in a row.) That keeps cost and noise down ([CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)).

### Background tasks are first-class in all three CLIs, and machdoch currently kills them

Claude Code has the most complete and best-documented background model. In an open stream-json session, `task_started` identifies shells and Monitor watches (`local_bash`), subagents (`local_agent`) and remote agents, with `task_id`, `is_backgrounded`, `spawn_depth` and `parent_task_id`. `task_progress` adds token and tool counts, plus a one-line summary when `agentProgressSummaries` is on, `task_updated` patches the status, and `task_notification` reports completion with an output file and usage. `background_tasks_changed` (2.1.203+) delivers the full live set, and hosts should replace their copy on each payload ([TS reference](https://code.claude.com/docs/en/agent-sdk/typescript#sdkbackgroundtaskschangedmessage)). The controls are `stop_task`; `background_tasks`, the Ctrl+B equivalent that moves a foreground command or subagent to the background; and the undocumented `get_task_output`, which returns the last 8 KiB of a shell's output for polling ([sdk.d.ts](https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk?activeTab=code)). The decisive flag is `perTaskStopAffordance`. When a host declares that it renders per-task stop buttons, an interrupt aborts only the turn and spares background agents. Without the declaration, an interrupt kills them ([TS SDK CHANGELOG 0.3.246](https://github.com/anthropics/claude-agent-sdk-typescript/blob/main/CHANGELOG.md)). When background work finishes, the CLI can inject a follow-up turn whose `result` carries `origin.kind: "task-notification"`. machdoch must be ready for turns the user did not start ([TS reference, SDKResultMessage](https://code.claude.com/docs/en/agent-sdk/typescript#sdkresultmessage)). Unattended runs have limits: background Bash defaults to 30 minutes (10 minutes in a `-p` run with a text prompt), and Monitor watches time out after 5 minutes in `-p` ([Tools reference](https://code.claude.com/docs/en/tools-reference)).

Codex exposes background work only through the app-server. Long-lived terminals that the agent starts run under the stable `unified_exec` feature and are listed and stopped with `thread/backgroundTerminals/list`, `clean` and `terminate`, which are experimental. `command/exec` is a stable process runner that is not tied to a thread, with PTY, stdin and streamed output, and machdoch could use it for its own terminal panel. `process/*` spawns processes and requires `experimentalApi` ([App-server docs](https://learn.chatgpt.com/docs/app-server)). Goals are the other long-running mechanism. They continue automatically until `complete`, `budgetLimited` or `usageLimited`, so they need a live, subscribed app-server ([TS:ThreadGoalStatus](file:///C:/Users/ehrha/AppData/Local/Temp/claude/C--Development-machdoch/dd3e5508-041e-4930-b633-c0e644aa1f2e/scratchpad/cx-ts-exp/v2/ThreadGoalStatus.ts)). `codex exec --json` gives no view of background work at all.

Copilot treats background shells and agents as tasks. The pinned crate has `session.tasks.list`, `getProgress` (with `recentOutput`), `cancel`, `sendMessage`, `promoteToBackground` and `startAgent`. Each `TaskShellInfo` separates attached PTY shells from detached processes and carries the pid and log path. `session.background_tasks_changed` signals a change without a payload ([crate api_types.rs](file:///C:/Users/ehrha/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/github-copilot-sdk-1.0.7-preview.2/src/generated/api_types.rs)). Shells promoted to the background keep running after the turn (1.0.62), non-interactive runs wait for background agents before exiting (1.0.33), and messaging a running background agent steers its turn (1.0.92) ([copilot-cli changelog](https://github.com/github/copilot-cli/blob/main/changelog.md)). Two newer controls exist only on main: cursor-based output reads (`tasks.readOutput`), and `interruptMainTurn`, which stops the main turn but leaves background work alive ([SDK-main rpc.rs](https://github.com/github/copilot-sdk/blob/main/rust/src/generated/rpc.rs)).

Detached and cloud variants exist, but they are not APIs a host can embed. `claude --bg` cannot be combined with `-p`, and `claude agents --json` is "the supported way to read session state from outside Claude Code" ([Agent view](https://code.claude.com/docs/en/agent-view)). Cloud scheduled tasks via `/schedule` are a research preview that runs off the device ([Routines](https://code.claude.com/docs/en/routines)), and `codex cloud` is experimental. machdoch's Smart Scheduler and fleet already cover those use cases. Claude offers a better fit: a host can declare its own scheduled runs with `CLAUDE_CODE_HOST_SCHEDULED_RUN=1` and an `origin` of `task-notification`/`scheduled-trigger` (SDK 0.3.280+) ([TS reference](https://code.claude.com/docs/en/agent-sdk/typescript#declare-a-scheduled-run)).

The product decision machdoch needs is a three-level stop policy. **Stop turn** interrupts through the protocol and spares background work (Claude `interrupt` with `perTaskStopAffordance`, Codex `turn/interrupt`, Copilot `abort`). **Stop task** targets one process (`stop_task`, `backgroundTerminals/terminate`, `tasks.cancel`). **Close session** ends everything. Until persistent sessions land, the fixed ten-second kill should give way to the CLI's own exit logic, plus a visible "stop background work" control. Claude's idle cap can be tuned with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` ([Headless](https://code.claude.com/docs/en/headless)).

## Native drivers behind an ACP-shaped core beat ACP alone

ACP is the serious alternative. Version 1 is stable JSON-RPC over stdio, with features gated by capabilities. Between February and September 2026 it stabilized session list, resume, close and delete, config options, `usage_update` (context-window use and optional cost), elicitation, request cancellation and message IDs ([ACP Updates](https://agentclientprotocol.com/updates)). All three targets can be reached over ACP: Claude through `claude-agent-acp`, built on the Agent SDK; Codex through `codex-acp`, rebuilt on the app-server after the original Zed repository was archived on 2026-07-22 ([codex-acp](https://github.com/agentclientprotocol/codex-acp)); and Copilot natively with `copilot --acp`, in public preview since 2026-01-28 ([GitHub changelog](https://github.blog/changelog/2026-01-28-acp-support-in-copilot-cli-is-now-in-public-preview/)). The ACP Rust SDK reached 1.0 on 2026-06-25, and the agents page lists 48 agents ([ACP Agents](https://agentclientprotocol.com/overview/agents)). Zed, which hosts external agents over ACP, shows it works in production ([Zed External Agents](https://zed.dev/docs/ai/external-agents)).

The problem is coverage at the edges machdoch cares about. Stable ACP has no rate-limit primitive and no prompt suggestions. Steering exists only as the pre-standard `_session/steering` extension in the Claude and Codex adapters, with no evidence that Copilot's ACP server supports it ([codex-acp steering.md](https://cdn.jsdelivr.net/gh/agentclientprotocol/codex-acp@main/docs/steering.md)). Goals and background-terminal control arrive only through JetBrains AIR `_meta` extensions, review exists only as Codex slash commands, and subagent sessions are still a draft RFD ([claude-agent-acp README](https://cdn.jsdelivr.net/gh/agentclientprotocol/claude-agent-acp@main/README.md)). Copilot's ACP server fixes tool filtering and reasoning effort at launch, and its `session/new` accepts only cwd and MCP servers. machdoch's per-task model, effort and context presets would therefore need one process per policy, and `--fleet` is unsupported ([ACP server docs](https://docs.github.com/en/copilot/reference/copilot-cli-reference/acp-server); [programmatic reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-programmatic-reference)). The adapters also add a hop and a delay, because new features land in the native protocols first. `codex-acp` bundles its own `@openai/codex`, which can differ from the user's installed 0.159.1 unless `CODEX_PATH` overrides it. And ACP v2 has been a draft since 2026-07-20 and changes the prompt lifecycle and session methods, so a v1 integration built now faces a migration ([ACP v2 overview](https://agentclientprotocol.com/protocol/v2/overview)).

| Option | What machdoch gains | What it gives up or pays | Verdict |
|---|---|---|---|
| ACP as the only protocol | One client for all three CLIs and about 45 more agents. Covers sessions, prompt, cancel, tool calls, plans, slash commands, config options, list/resume and `usage_update` | No rate limits or suggestions. Steering, goals and background control only through vendor extensions; review only as Codex slash commands. Adapter delay. Copilot settings fixed at launch. A v2 migration ahead | Not as the primary path |
| Three native drivers | Every capability in the matrix, building on the protocol footholds machdoch already has | Three protocols to maintain, experimental fields, and a schema per version | Necessary, but without a shared model each feature is built three times |
| Hybrid: native drivers behind an internal model shaped like ACP v2 | Full native depth, one UI model, and an optional ACP driver for extra agents later | Up-front design of the internal model | **Recommended** |

The hybrid's key move is to borrow ACP's schema, not its transport. ACP v2's lifecycle is a ready-made template for machdoch's internal model. A prompt is accepted with a `messageId`; a `state_update` reports `running`, `requires_action` or `idle` with stop reasons (`end_turn`, `max_tokens`, `refusal`, `cancelled`, `error`); background activity may continue while the session is idle; `usage_update` carries `used`, `size` and an optional cost; and notices carry a severity ([ACP v2 Prompt Lifecycle](https://agentclientprotocol.com/protocol/v2/prompt-lifecycle.md)). Those states map directly onto machdoch's task queue and attention UI. Each native driver translates into that model, and an ACP driver can later join as a fourth, generic driver for Gemini CLI, OpenCode or others without touching the UI. For queue semantics, codex-acp's `idleBehavior: "promptRequired"` steering outcome shows the right split of ownership: the host keeps its own queue authoritative and sends queued input as a normal prompt ([codex-acp steering.md](https://cdn.jsdelivr.net/gh/agentclientprotocol/codex-acp@main/docs/steering.md)). This also avoids Codex's experimental `thread/queue/*`.

The remaining design choice is where each driver runs. The Claude and Codex drivers belong where machdoch already spawns runs, the Node/TypeScript runtime sidecar. It already parses Claude stream-json and holds an app-server client, and `codex app-server generate-ts` emits TypeScript bindings for each CLI version ([App-server docs](https://learn.chatgpt.com/docs/app-server)). Claude offers a genuine choice. The official TS Agent SDK is the documented contract and supplies helpers that exist only in the library (`listSessions`, `getSessionMessages`, `forkSession`), at the price of tying machdoch to the SDK's CLI version, since SDK 0.3.N ships CLI 2.1.N. Speaking the raw protocol with vendored `sdk.d.ts` types keeps machdoch on the user's installed CLI but relies on an undocumented wire contract ([TS SDK reference](https://code.claude.com/docs/en/agent-sdk/typescript#query-object)). For Copilot, keeping the driver in Rust reuses the crate already linked for discovery. The Node package `@github/copilot-sdk` 1.0.28 would instead put all three drivers behind one translation layer ([npm registry](https://registry.npmjs.org/@github/copilot-sdk)). Either way, the SDK and CLI must be pinned as a pair, per the crate's own warning that "the SDK and CLI are versioned together" ([crate README](file:///C:/Users/ehrha/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/github-copilot-sdk-1.0.7-preview.2/README.md)).

## A four-phase roadmap moves from data already streamed to persistent sessions

The phases are ordered by what each one changes. **Phase 0** changes only flags and parsing. **Phase 1** changes the transport but keeps one process per turn and keeps re-sending history, so machdoch's memory, summaries and branch features keep working untouched while the protocol drivers mature. **Phase 2** changes who owns conversation state, which is the highest-leverage step and the biggest commitment. **Phase 3** adds optional extensions on top. The effort labels are my rough single-engineer estimates, not figures from the sources: **S** is up to a week, **M** two to four weeks, **L** one to three months. The test numbers refer to the live tests in the last section.

Phase 0 is cheap because the data is already in the streams. Claude's `rate_limit_event` carries five-hour and seven-day utilization and reset times, and it appeared in machdoch's own test log ([local test log](file:///C:/Users/ehrha/AppData/Local/Temp/claude/C--Development-machdoch/dd3e5508-041e-4930-b633-c0e644aa1f2e/scratchpad/suggest.jsonl); [TS reference, SDKRateLimitEvent](https://code.claude.com/docs/en/agent-sdk/typescript#sdkratelimitevent)). `result.modelUsage` carries per-model `contextWindow` and covers subagents and compaction, which is why the docs recommend it over `usage` ([Cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)). Dollar figures belong only in front of API-key users, because `total_cost_usd` is a client-side list-price estimate that subscription users are not billed. Codex review needs no app-server: `codex exec review` accepts `--uncommitted`, `--base` or `--commit` together with `--json` and `--output-schema` (local `codex exec review --help`, 0.159.1). The Codex fast toggle is `-c service_tier="fast"`, shown only when the model lists a `priority` tier in its `service_tiers` ([Config reference](https://learn.chatgpt.com/docs/config-file/config-reference)), and Claude's is `--settings '{"fastMode":true}'`, with `fast_mode_disabled_reason: "sdk_opt_in_required"` signalling a missing opt-in ([Fast mode](https://code.claude.com/docs/en/fast-mode)).

The remaining Phase 0 items harden what already runs. Codex goals can drop `experimentalApi` entirely, because `thread/goal/*` is in the stable set, and unhandled server requests should get a typed decline or cancel instead of -32601. On Windows, `CLAUDE_CODE_STARTUP_FAILURE_RESULTS=1` turns silent startup refusals, such as a missing shell tool, into results with a `startup_failure_reason` ([TS reference](https://code.claude.com/docs/en/agent-sdk/typescript#sdkresultmessage)). Cancel should send SIGINT first so the turn records a result, and kill only if the process does not exit, because SIGTERM exits with code 143 and leaves the turn unrecorded ([Headless](https://code.claude.com/docs/en/headless)). And because `--include-partial-messages` and `--forward-subagent-text` need no control channel, machdoch can stream Claude text live before Phase 1 begins.

Phase 1 is where most of the visible UX arrives. For Claude, switching to `--input-format stream-json` and holding stdin open until `result` and its trailing events lets machdoch implement its existing but unimplemented "steer" option as `priority: "next"` (machdoch source), a "send now" as `priority: "now"`, and stop as `interrupt` with `cancel_queued`. Adding `--permission-prompt-tool stdio` while staying in bypass mode enables question cards, because `AskUserQuestion` reaches the host in every mode ([SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)), and the answer format is documented: allow with the original `questions` plus an `answers` map ([Handle approvals and user input](https://code.claude.com/docs/en/agent-sdk/user-input)). For Codex, routing ordinary chat turns through the app-server client machdoch already has, on an ephemeral thread per run, yields `turn/steer`, `turn/interrupt`, deltas, `turn/plan/updated`, `turn/diff/updated`, `thread/tokenUsage/updated`, `account/rateLimits/updated`, `review/start` and `serviceTier`, all stable. For Copilot, Phase 1 starts with the crate upgrade and then drives turns through SDK sessions, with `send` in `immediate` or `enqueue` mode, `abort`, `streaming: true`, and user-input and exit-plan handlers in place of `--no-ask-user`. The deliverable shared by all three is a "needs input" state that routes questions to the chat, to notifications and to fleet devices, following Claude Remote Control's pattern of a push notification whenever an action is required ([Remote Control](https://code.claude.com/docs/en/remote-control.md)).

Phase 2 stops re-sending history. A supervisor keeps one long-lived Claude process per active chat, one Codex app-server that multiplexes threads, and one Copilot client that multiplexes sessions. It evicts idle sessions and resumes them by id. Two vendors already do the same: Claude agent view stops idle unattached sessions after about an hour and resumes them from disk ([Agent view](https://code.claude.com/docs/en/agent-view)), and Codex unloads a thread 30 minutes after its last subscriber leaves ([App-server docs](https://learn.chatgpt.com/docs/app-server)). machdoch's memory and summaries then enter as context rather than as transcript text. Claude accepts a user message with `shouldQuery: false`, which appends context without starting a turn ([TS reference](https://code.claude.com/docs/en/agent-sdk/typescript#sdkusermessage)). Codex's stable `thread/inject_items` appends raw Responses items to the history the model sees ([TS:ThreadInjectItemsParams](file:///C:/Users/ehrha/AppData/Local/Temp/claude/C--Development-machdoch/dd3e5508-041e-4930-b633-c0e644aa1f2e/scratchpad/cx-ts-exp/v2/ThreadInjectItemsParams.ts)). For Copilot, customizing sections of `system_message` is the nearest equivalent.

Branch and edit map onto native forks: Claude `--resume <id> --fork-session --resume-session-at <uuid>`, Codex `thread/fork` with `lastTurnId` or `thread/revert`, and Copilot `sessions.fork` with `toEventId`. File restoration should stay with machdoch's own file-change tracking. Codex revert never touches files. Claude's file rewind needs checkpointing from session start and ignores Bash edits. Copilot's rewind that also restores files exists only on main and is "not crash-atomic" ([File checkpointing](https://code.claude.com/docs/en/agent-sdk/file-checkpointing); [SDK-main rpc.rs](https://github.com/github/copilot-sdk/blob/main/rust/src/generated/rpc.rs)). Persistent sessions also keep the prompt cache warm, which makes Claude suggestions routine instead of occasional.

Phase 3 is optional. Host tools without MCP sidecars become possible through Codex `dynamicTools` (an experimental declaration with a stable `item/tool/call` reply, persisted and restored on resume), Claude's in-process SDK MCP servers tunnelled as `mcp_message`, and Copilot's client tools ([App-server docs](https://learn.chatgpt.com/docs/app-server); [Custom tools](https://code.claude.com/docs/en/agent-sdk/custom-tools)). machdoch's current `--mcp-config`/`--strict-mcp-config` path works, so this is an optimization, not a fix. A generic ACP driver for additional agents comes last.

## Experimental surfaces and version skew set the risk budget

### Stability and version skew demand pinned pairs and lenient parsers

Copilot is the largest technical risk. Every deep Copilot capability machdoch would use is a generated RPC under an experimental banner. The wire schema grew from 255 methods and 106 event types in the pinned crate to 587 and 150 on main ([crate session_events.rs](file:///C:/Users/ehrha/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/github-copilot-sdk-1.0.7-preview.2/src/generated/session_events.rs); [SDK-main session_events.rs](https://github.com/github/copilot-sdk/blob/main/rust/src/generated/session_events.rs)). The fix is to treat crate and CLI as one dependency. One way is to enable the crate's bundled CLI; machdoch builds with `default-features = false`, so today it finds the CLI by path. The other is to enforce a tested CLI version at startup. The repository README and the crate README disagree on whether the Rust SDK bundles the CLI by default, so verify this on the chosen version ([copilot-sdk README](https://github.com/github/copilot-sdk); [crate README](file:///C:/Users/ehrha/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/github-copilot-sdk-1.0.7-preview.2/README.md)).

For Codex, generate bindings from the installed binary at build time, and probe `experimentalFeature/list` and `model/list` at runtime. The documentation runs ahead of 0.159.1, and some of it conflicts with the schema. The docs page shows camelCase enum values where the local schema uses kebab-case, and `requestUserInput` is stable in the schema but labelled experimental in the docs ([App-server docs](https://learn.chatgpt.com/docs/app-server)).

For Claude, near-daily releases and many internal fields argue for lenient parsing. machdoch should ignore unknown stream-json message types and fields, and gate every optional feature on `system/init.capabilities` and `claude_code_version` ([TS reference, SDKSystemMessage](https://code.claude.com/docs/en/agent-sdk/typescript#sdksystemmessage)). The docs also conflict on whether 2.1.302 made `-p` start in Manual mode in general or only on third-party providers ([Headless](https://code.claude.com/docs/en/headless); [CHANGELOG 2.1.302](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). This does not affect machdoch as long as it always sets a permission mode explicitly. Across all three CLIs, replaying recorded transcripts for each pinned version in CI catches regressions cheaply.

### Instruction isolation moves from guaranteed by design to maintained by configuration

Today, machdoch's instruction isolation is built into the invocation itself: an empty `--setting-sources`, strict MCP config, a throwaway CODEX_HOME and a run-scoped Copilot agent (machdoch source). With persistent sessions, those guarantees hold only if every resume repeats them, and the system prompt behaves in the opposite, sticky way.

For Claude, settings sources and MCP config are launch flags, so each resumed process must pass them again. The system prompt, by contrast, is frozen: `--system-prompt-snapshot on`, the default, records it on the first request and reuses it on every later request and resume until compaction, "even when a later launch passes different text" ([local `claude --help`](file:///C:/Users/ehrha/AppData/Local/Temp/claude/C--Development-machdoch/dd3e5508-041e-4930-b633-c0e644aa1f2e/scratchpad/claude-help.txt)). **An updated machdoch instruction will not reach an existing session** unless snapshotting is off or the session starts fresh. Transcripts land in the user's own `~/.claude/projects/` unless relocated with `CLAUDE_CONFIG_DIR` or named with `CLAUDE_CODE_PROJECT_DIR_NAME` ([Sessions](https://code.claude.com/docs/en/agent-sdk/sessions)), and `--bare`, which skips CLAUDE.md discovery and hooks, requires API-key auth and so cannot isolate subscription users. Codex needs a persistent CODEX_HOME owned by machdoch with a stable config.toml, with per-run instructions and MCP servers passed through `developerInstructions` and `config` on `thread/start` and passed again on every `thread/resume`, because 0.159.1 predates the restoration of saved settings; spawned subagents inherit `developer_instructions`, as machdoch verified.

Copilot needs the most care. `ClientMode::Empty` skips custom instructions, keeps custom agents local and turns memory off, and from SDK 1.0.13 also drops built-in skills, a default the pinned crate predates ([crate mode.rs](file:///C:/Users/ehrha/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/github-copilot-sdk-1.0.7-preview.2/src/mode.rs)). But Copilot also loads hooks from `.claude/settings*.json` and rules from `.claude/rules` ([hooks configuration](https://docs.github.com/en/copilot/reference/hooks-configuration); [copilot-cli changelog](https://github.com/github/copilot-cli/blob/main/changelog.md)), so **a repository's Claude configuration can reach Copilot runs**, and whether `ClientMode::Empty` or `--no-custom-instructions` suppresses that is unverified. Copilot sessions also accept multiple clients, and a client without a handler defers to another connected client ([crate README](file:///C:/Users/ehrha/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/github-copilot-sdk-1.0.7-preview.2/README.md)), so machdoch should connect over stdio and never expose a session to a second client.

### Cost and resource budgets need explicit limits

Deeper integration spends more tokens in less obvious places. Claude suggestions bill against plan limits, Codex fork-based suggestions cost a full small turn each, and `get_context_usage` with `detail: "full"` makes token-counting API calls, so only the `summary` detail is cheap enough to run after every turn ([TS reference](https://code.claude.com/docs/en/agent-sdk/typescript#sdkcontrolgetcontextusageresponse)). Usage figures are not always comparable either. Copilot's nano-AIU-to-AI-Credit conversion is not documented, and so far nothing says which `quotaSnapshots` key holds the AI-credit budget ([SDK usage docs](https://github.com/github/copilot-sdk/blob/main/docs/features/usage-and-billing.md)). Codex reports no currency at all. Subscription users are therefore best served by plan-window percentages rather than dollar figures. Each long-lived process also holds memory, which is why idle eviction belongs in Phase 2 rather than later. Finally, Codex feeds `clientInfo.name` into its Compliance Logs Platform and asks enterprise integrations to join its known-clients list, which is worth doing before machdoch ships an app-server driver widely ([App-server docs](https://learn.chatgpt.com/docs/app-server)).

## Seventeen live tests settle what the documentation leaves open

Each open question below can be settled with a single short run against the installed binaries, and most gate a roadmap item. None needs more than a scratch project and a few prompts.

| # | CLI | Open question | Smallest live test |
|---|---|---|---|
| 1 | Claude | Does one-shot `-p --prompt-suggestions` emit `prompt_suggestion` after a turn that used tools? | Run a two-tool prompt with the flag; log every stdout line until exit |

## Conclusion

The research reframes the integration problem. machdoch does not lack access to advanced features. It lacks a live control channel, and how long that channel lives, one turn or one session, decides which features it gets. A control channel held open for one turn already delivers steering, graceful stop, in-app questions, live progress and usage, without touching machdoch's memory, summaries and branching. That is why it should come before the persistent-session rewrite, not after it. The vendors' maturity labels are an unreliable guide to risk. The Codex app-server, whose subcommand is labelled experimental, has the most stable-marked host schema, while the GA Copilot SDK marks every wire method experimental. machdoch's version gates and contract tests should therefore follow per-method stability tags and pinned SDK–CLI pairs, not product labels.

The integration also changes what machdoch's own features need to do. Several of them now have native counterparts: persistent goals in Codex `thread/goal/*` and Claude `/goal`, queued messages in Claude's priority-tagged user messages and Codex `turn/steer`, the Smart Scheduler in Claude's host-declared scheduled runs, and fleet remote control in Remote Control's outbound-only design. The right split is that machdoch owns the queue, the schedule and the attention model, and the CLIs own turns. Native primitives should replace machdoch's workarounds, but should not replace machdoch's role as the source of truth. Follow-up suggestions, the user's first example, are the clearest case for a UI that works the same for every provider. They are native and nearly free on Claude once sessions persist, and machdoch must generate them for Codex and Copilot. The `followUps` shape that machdoch's API runtime already uses is the obvious common format.
