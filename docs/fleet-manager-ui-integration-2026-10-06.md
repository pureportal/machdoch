# Fleet UI integration — 2026-10-06

The client, Fleet dashboard, and Fleet remote view now share their application frame, responsive navigation, appearance controls, and palette. The complete goal of exposing every client feature remotely remains unfinished.

## Changes

- `packages/product-ui` owns `ApplicationShell`, `ApplicationNavigation`, appearance normalization/application, and `AppearanceOptions`. Native Chat, Fleet's dashboard, and Fleet `ProductShell` compose the same frame and navigation. Each retains its host-specific content and command handling.
- Fleet dashboard components use the client's semantic theme tokens. The separate dashboard palette, remote product recoloring, and embedded Media/RALPH palette overrides were removed.
- Appearance on Fleet's Users page controls theme, accent, and density. Browser preferences survive navigation and synchronize between Fleet pages and embedded Media/RALPH views. The native settings panel uses the same controls and its existing native persistence.
- The headless Fleet service now persists per-session global-memory changes and honors them in subsequent task context. Replayed commands preserve their receipt across a service restart.
- Native and remote Smart Scheduler use `packages/client-ui` for the complete form, job/run views, mutations, deletion confirmation, and command palette. A scoped Scheduler protocol routes commands to the existing scheduler engine on native and headless hosts. The headless host runs persisted schedules and imports scheduled prompt definitions automatically.
- Gateway response correlation now covers every request type explicitly. A real relay failure exposed the missing Scheduler mapping; websocket regression tests cover Media, RALPH, and Scheduler replies.
- The production browser harness checks the built client and manager together, shared colors, mobile navigation, session creation, draft retention, and appearance persistence. Its existing enrollment, settings merge/conflict, Copilot, RALPH, outage, restart, and revocation checks remain enabled.

## Remaining verification

The fixture uses isolated CLI services, offline workspaces, and fixture API keys. It can establish real relay/persistence/browser behavior, but cannot establish provider-backed task completion, native desktop enrollment/control, voice input/output, or actual GPU media generation. Those need a running native host and configured providers/models. No development server was started for this work.

The CLI bundle, Fleet build, and complete production browser campaign passed. Screenshots in `.tmp/fleet-verification/1791250727832/` include the built client, dashboard, device Chat, embedded Media, and shared Scheduler on desktop/mobile. The built client check uses browser preview behavior; it does not prove native IPC execution.

The embedded Scheduler command palette was opened through its actual keyboard shortcut. Full native settings, the complete application keyboard bindings, provider-backed execution, native desktop enrollment/control, voice, GPU generation, and the missing remote workflows listed above still need parity or execution verification. The overall goal remains open.

Existing reports describe prior verification; they do not establish full parity for these changes: [remote RALPH](fleet-manager-ralph-editor-verification-2026-10-05.md) and [Fleet continuation](fleet-manager-continuation-2026-10-05.md).
