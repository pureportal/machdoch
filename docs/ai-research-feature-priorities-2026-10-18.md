# Machdoch AI research and feature priorities

Research date: 18 October 2026. Repository baseline: `8c631d0f` plus the working tree available during the review. This is a research and product recommendation; no application features were implemented.

**Recommendation: prioritize dependable execution, current memory, and a searchable multimodal workspace.** Add a research workflow, reusable skills learned from successful work, and interactive tool results on that foundation. These investments apply across providers and strengthen Chat, RALPH, scheduling, Fleet, and Media Studio together.

The rankings below are engineering judgments about Machdoch's fit, usefulness, implementation dependencies, and likely durability. They are not benchmark results or forecasts. Research outcomes belong to the authors' evaluated settings. Provider documentation establishes a published capability, not successful integration or availability to a particular account.

**Research scope.** The investigation covered recent agent memory, context management, skill learning, verification, multi-agent systems, visual document retrieval, computer use, realtime voice, generative interfaces, media control, and inference acceleration. It emphasized 2026 publications and releases, including work from October 2026, while retaining older foundations where their updated results remain relevant. Findings rely on papers, author publications, official specifications, model cards, and provider documentation. Selected full-text methods and limitations were examined for MemTrace, SkillNEO, Recursive Language Models, and agent scaling; other paper entries are primarily abstract and release-record assessments. This is a targeted product research review, not an exhaustive systematic literature review.

**Recommended order.** P1 means the strongest next investment; P2 means pursue after its prerequisites or when the associated product area is the current focus. M means a coherent change across several modules; L means a substantial runtime, storage, or interface addition. These are relative complexity judgments, not delivery estimates. Ranking confidence measures product fit, not the certainty of a paper's reported gains.

**1. Completion backed by current outcome evidence.** Extend the current goal evaluator with a durable record of the requested outcome and evidence for each requirement. The existing evaluator already receives observed tool evidence, which is a useful base. The gap is giving the system a reliable way to obtain and bind evidence to the resulting state, beyond judging the final transcript.

For a file transformation, verify the produced files and content. For a browser task, inspect the saved state or resulting artifact. For code, attach the relevant check result to the revision it tested. Collect these observations through constrained verification tools; keep the completion judge separate from the executor. Anthropic's [evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) distinguishes statements in a transcript from actual environment outcomes, while its [application harness study](https://www.anthropic.com/engineering/harness-design-long-running-apps) demonstrates independent browser-based evaluation.

Acceptance: deliberately false completion claims fail; checks run before a relevant change cannot certify the new result; cancellation and restart preserve the record. Expose useful evidence on demand through the existing task detail, without adding permanent explanatory UI.

**2. Memory that validates its evidence and handles changed facts.** Extend memory with source identifiers, relevant file hashes or external version markers, observed time, and explicit supersession. Restore a claim only after checking the state it depends on. A previously successful check becomes historical evidence after a relevant change; a user's corrected preference supersedes an earlier preference.

The proposal borrows validated restoration from [MemTrace](https://arxiv.org/html/2610.04838v3) and action-oriented evaluation from [AMA-Bench](https://proceedings.mlr.press/v306/zhao26bs.html). Start with direct evidence links and file dependencies; a full repository graph should be justified by measurements. User preferences and repository observations require different validity rules. File hashes alone cannot validate a remote service or an assertion about program behavior.

Acceptance: a changed file or corrected fact stops obsolete evidence being presented as current; relevant durable preferences survive; source deletion removes derived retrieval entries. Measure stale-memory errors and successful continuation across context refreshes.

**3. Local multimodal workspace search.** Create one index over selected workspace documents, code, images, audio transcripts, and video segments. Return the exact file, page, region, or timestamp supporting the result. Combine lexical matching with semantic retrieval and reranking where it improves measured recall.

[EmbeddingGemma 2](https://blog.google/innovation-and-ai/technology/developers-tools/embeddinggemma-2/) is a particularly timely local candidate. Evaluate page-image retrieval separately on scanned documents, charts, and tables; [Argus](https://arxiv.org/abs/2606.04300) and [MarginMerge](https://arxiv.org/abs/2608.02969) are relevant research leads if simple embeddings miss the required evidence. Index generation must be incremental, respect selected locations, and remove derived data when sources are removed. Local indexing does not imply that subsequent cloud answers remain local.

Example: “Find the chart about quarterly costs and the recording where we discussed it.” Acceptance should cover paraphrases, German/English queries, changed files, scanned pages, and timestamp accuracy. Measure retrieval quality, cold/warm latency, disk use, RAM, and GPU contention with media jobs before choosing a model/runtime.

**4. Efficient tool orchestration and selective schema loading.** Keep Machdoch's existing MCP catalog search, inspection, and asynchronous task support. Improve the model-visible tool set so unrelated schemas do not occupy every prompt. The current default hybrid exposure can expose discovered tools directly alongside meta-tools; source inspection is not a measurement of its actual token cost.

Add a bounded code orchestration facility that can invoke registered tools, combine independent reads, filter large outputs, and return compact results. Shell execution alone does not provide that tool-aware execution contract. Calls must retain the existing argument validation, Ask/Machdoch behavior, cancellation, and per-operation accounting. Combine write operations only where ordering and side effects are explicit.

Anthropic documents [on-demand tool loading and programmatic calls](https://www.anthropic.com/engineering/advanced-tool-use), and its [MCP code-execution study](https://www.anthropic.com/engineering/code-execution-with-mcp) demonstrates the efficiency rationale. These are design precedents; provider-specific mechanisms are not interchangeable.

Acceptance: equal or better success with lower schema and result tokens on a representative large tool catalog; retained audit visibility; bounded execution; no cross-call permission bypass. Measure median and tail latency as well as token counts.

**5. Research projects with claim-level sources and refresh.** Add a saved research task with questions, collected documents, claims, supporting passages, publication/access dates, conflicting evidence, and unresolved questions. Build it on the current search providers, history, goals, and RALPH. Source metadata belongs in the research artifact and inspection view, rather than a wall of interface instructions.

The workflow should open and assess sources, distinguish primary evidence from commentary, reconcile discrepancies, and check whether each significant claim is actually supported. [DeepWeb-Bench](https://arxiv.org/abs/2605.21482) makes this distinction especially relevant: retrieval volume is an incomplete proxy for research quality. Allow scheduled refresh through the existing scheduler and show material changes to the saved findings.

Example: monitor a dependency, technical field, supplier specification, or product shortlist. Acceptance: citations support adjacent claims, dates distinguish older papers from revised releases, unsupported claims remain unresolved, and refresh reports actual evidence changes. Use controlled question sets with deliberately contradictory and outdated sources.

**6. Skills distilled from verified runs.** Use the reasoning bank, recorded macros, and RALPH as inputs to a skill lifecycle. Extract a procedure with inputs, required tools, expected outputs, and checks; test it on new examples; publish a selected version to the reusable skill library. An unsuccessful candidate can remain available for offline development without being used for normal execution.

[SkillNEO](https://arxiv.org/html/2610.20926v1) motivates evidence-driven revision, but its same-instance evaluation makes unseen inputs a necessary Machdoch acceptance condition. [Skill revision research](https://arxiv.org/abs/2610.04832) and [ACE](https://arxiv.org/abs/2510.04618) also support evaluating concrete procedural improvements. Keep task-specific lessons scoped and treat imported procedures as untrusted until inspected and evaluated.

Acceptance: repeated work improves on held-out task variants without a cost or failure regression; failed candidates cannot replace the selected procedure; provenance and version history remain inspectable. This requires evaluated promotion, not simply saving every successful transcript.

**7. Interactive results through MCP Apps.** Add a host for the official [MCP Apps extension](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/), including resource discovery, isolated UI rendering, and a host-controlled tool bridge. Good first uses are an editable results table, a chart with filters, or a document viewer with cited passages. No MCP Apps host was identified in the inspected tracked client/package source.

The host must constrain the embedded resource's access and route actions through the same tool execution boundary as ordinary agent calls. A component must not gain native or filesystem access because it appears inside Machdoch. [A2UI](https://developers.googleblog.com/a2ui-and-mcp-apps/) is worth a narrower experiment where declarative components provide better consistency. Choose a clear rendering contract for each supported integration rather than creating competing general UI engines at once.

Acceptance: a real external app works, keyboard navigation is usable, tool action outcomes appear in the task history, and embedded resources cannot bypass host boundaries. Keep the existing interface conventions and add only controls that help the current task.

**8. Measured reasoning, model, and worker allocation.** Evolve the adaptive controller using actual outcomes. Select a model and reasoning budget appropriate to a bounded subtask, and assign workers when the work has useful independence. Preserve explicit user model choices and data-location constraints. A route change must be an intentional execution policy, not an undocumented fallback.

The existing controller uses heuristics and the internal model already handles supporting work. The addition is a measured policy over these capabilities. [Agent scaling research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/) supports evaluating task structure before adding workers. Small current models and [diffusion model APIs](https://www.inceptionlabs.ai/models) are candidates for inexpensive extraction or rewriting, subject to task-specific quality checks.

Acceptance: compare verified success per total cost and end-to-end latency under fixed budgets; include failed attempts, coordination, verification, and provider retries. Begin with understandable policies and local measurements; train a router only when enough representative data exists.

**9. Computer actions with explicit state checks.** Connect current semantic browser locators and desktop controls to a loop that observes the current state, selects an actionable target, performs one coherent action, and checks the consequence. Rediscover targets when the application changes. Extend accessibility coverage only where the platform APIs actually support it.

[Tactile](https://arxiv.org/abs/2607.14443) offers a useful architecture reference; [OSWorld 2.0](https://arxiv.org/abs/2606.29537) motivates testing long workflows and mid-task changes. Coordinate targeting remains a deliberate technique for visual surfaces, with current screenshots and validation. Do not describe existing semantic locators or Windows control enumeration as new features.

Acceptance: tolerate a moved window, delayed UI update, changed page state, and recoverable target failure; verify saved outputs. Prioritize Windows and Linux scenarios matching Machdoch's supported platforms. Integrate observations with the evidence record from item 1.

**10. Realtime voice companion.** Add an optional continuous conversation session with interruption, streaming replies, and task delegation. The user should be able to correct an instruction while a task is running and receive an accurate account of its state. Shared screen or window input should be explicitly selected for that session.

[OpenAI's voice architecture guide](https://developers.openai.com/api/docs/guides/voice-agents) makes a separate voice interface over an existing task backend particularly relevant to Machdoch. [Realtime API](https://developers.openai.com/api/docs/guides/realtime) and [Gemini Live](https://ai.google.dev/gemini-api/docs/live-api/capabilities) provide implementation candidates with different maturity and execution models. Use the current TTS suite proposal for directed narration; a narration model is not automatically the best conversational model.

Acceptance: interruption stops stale playback, cancellation reaches the delegated task, reconnect does not repeat side effects, and the voice accurately distinguishes working, failed, and finished states. Measure time to first audible response and task accuracy. Inspect current voice model IDs against the provider's [deprecation schedule](https://developers.openai.com/api/docs/deprecations) during implementation.

**11. Editable spatial media composition.** Continue the existing layout proposal with a canonical editable scene: assets, text, transforms, regions, and relationships. Compile it into a supported model's native layout representation or deterministic composition operation. Keep exact typography and geometry in the scene when those are required, and verify generated object placement separately.

[FLUX 3 Image Klein](https://bfl.ai/blog/flux-3-image-klein) is a timely adapter candidate alongside the already researched models. Its published local and API capabilities require distinct runtime verification. The [hosted box interface](https://docs.bfl.ai/flux_3/flux3_image_bounding_boxes) establishes structured spatial inputs; it does not prove every local pipeline preserves pixels identically. Evaluate references, edit masks, output dimensions, and actual changes outside the requested area.

Acceptance: a user can reposition an element, revise its content, retain editable text, and regenerate the intended region. Check licensing for distribution and commercial use, and benchmark supported hardware. Reuse the [existing scene/layout research](media-studio-layout-control-research-2026-10-18.md) and the [TTS suite](text-to-speech-suite-plan-2026-10-18.md) for multimedia projects rather than starting parallel product designs.

**12. Bounded recursive analysis of large collections.** Pilot an analyst that stores a corpus outside the prompt, searches and processes it through code, delegates narrowly bounded questions, and assembles an answer with source references. [Recursive Language Models](https://arxiv.org/html/2512.24601v3) provide the main research basis.

This is useful for large document collections, repository audits, logs, and long media transcripts. It is not unlimited context. Bound recursion depth, total inference, tool calls, wall time, and output size, and keep subcall lineage in the task record. Compare with ordinary retrieval and the current agent before adopting it broadly.

Acceptance: improve answer coverage on large corpora under the same total budget, retain evidence for each conclusion, and stop cleanly on unproductive recursion. Tail cost and answer completeness matter as much as median performance.

**A practical starting sequence.** Implement a shared evidence record and a small task-evaluation set first. Add memory validity checks to that record. Build an incremental workspace index, then use it and the current web tools for research projects. Tool exposure optimization can proceed alongside indexing. Skills, routing, and more autonomous computer work should consume these measured outcomes. MCP Apps can be a separate product increment; realtime voice and media composition can follow the areas the team chooses to emphasize. No calendar estimate is implied.

The first evaluation set should use real Machdoch work: a file transformation, a small coding change, a browser workflow, a research comparison, a long task with a mid-run correction, and a media edit. Use clean fixtures and saved source inputs. Keep separate development and held-out variants. Add changed-file, stale-evidence, cancellation, and repeated-action cases where the relevant feature needs them. Measure verified success, false completion, total cost, latency, and user corrections. A new research system is justified when it improves these outcomes.

**Verification and limits of this review.** Official pages and primary research records were checked online and compared with relevant tracked source, the README, provider compatibility work, and the two current media/voice proposals. Local references in this report were checked for existence. No model benchmark was reproduced, no provider account capability was tested, and no application was started. Inference latency, hardware memory use, model quality, and integration effort remain hypotheses to validate in focused spikes. Existing repository tests were not run because only this research report was added. New features remain recommendations for selection and implementation.
