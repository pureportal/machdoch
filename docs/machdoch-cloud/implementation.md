## MCP implementation evidence

The authenticated Streamable HTTP endpoint is `/api/v1/mcp`. It uses the installed MCP SDK and the existing planning, comments, poker and execution services. Each service transaction rechecks the delegated token and current membership; browser sessions and runner credentials do not authenticate MCP. Provider credentials and private chat history are not exposed as tools. Read, planning-write and execution scopes are separate; consent defaults to read. Membership role changes or suspension permanently revoke existing grants, and users can disconnect their own apps.

OAuth uses a pre-registered public Machdoch client with the existing loopback callback, mandatory S256 PKCE, exact redirect/resource binding, hashed single-use codes and tokens, one-hour access tokens, rotating refresh tokens and a 30-day absolute grant lifetime. Refresh replay commits grant revocation. Each account can have 20 active connections. Authorization requests and browser approval are separate, and approval requires the authenticated browser's CSRF proof. Third-party client registration and metadata-document registration are not implemented. Pre-registration is a current mechanism in the [MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); deprecated dynamic registration was not added.

The desktop callback now validates the recorded issuer and state before accepting a code or an authorization error. A live two-workspace test initially reproduced refresh-token replay caused by concurrent connections. Refresh exchange now takes the existing cooperative file lock, persists the rotated credential before releasing it, and lets waiting connections adopt the stored result. Ambiguous network failures are not automatically retried. The same browser test then passed with one refresh exchange. Native source integration is exercised; the installed desktop binary has not been rebuilt.

Verification passed: the full 77-test cloud suite, then the expanded focused 12-test OAuth suite; 42 focused native MCP/client tests; client core/test type checking; focused lint; production builds; and seven Chromium scenarios through the real native client. `pnpm --filter @machdoch/cloud verify:cloud:mcp` reruns the browser/native check using the standard fixture. Task tests verify admission and cancellation in the durable control plane; they do not claim that a sandbox worker executed repository code.

## Repository delivery evidence

The runner repository endpoint accepts only `advertise` and `fetch` operations. It derives the GitHub destination from the immutable task manifest, checks current runner/attempt authority before opening a connection and before releasing the downloaded result, and refuses redirects. Git parsing, object import and checkout execute in the guest. The guest reaches a loopback HTTP gateway whose requests cross the existing supervised channel; there is no external network adapter, general URL proxy, Git push endpoint or provider credential in that gateway.

The transfer ledger limits each response to 64 MiB, each run to 512 MiB and 128 transfers, pending organization requests to four, and local in-memory responses to eight. Local capacity is retained until response consumption/cancellation; a bounded response lifetime prevents abandoned streams from retaining it indefinitely. Unknown/failed transfers retain their reservations. Completed read transfers require a new transfer ID for another request; this endpoint does not replay mutations. Gzip request encoding is preserved because current Git clients compress larger upload-pack requests. Protocol references: [Git HTTP protocol](https://git-scm.com/docs/http-protocol) and [Git remote-curl implementation](https://raw.githubusercontent.com/git/git/master/remote-curl.c).

The first real clone failed because the minimal guest's loopback interface was down. A direct VM probe returned interface flags `0x8`. Guest boot now brings up loopback before dropping privileges, while QEMU continues to use `-nic none`. The corrected guest fetched `octocat/Hello-World` at commit `7fd1a60b01f91b314f59955a4e4d4e80d8edf11d`; Git object integrity and README content passed. A separate compressed `ls-refs` request also passed. Cancellation rejected further source access, and the task UI retained the repository and base commit after the worker stopped.

## Durable output evidence

## Magic-link authentication and email delivery evidence

Magic-link requests return the same response for known and unknown addresses. Tokens are hashed for verification, expire after ten minutes and are consumed only by an explicit confirmation. Different devices can complete a link. User credential and membership changes advance a database generation; old links, sessions and MCP grants cannot revive after disable/re-enable cycles. Mail sign-in policy changes invalidate outstanding links without changing the permissions of an already authenticated session.

The dispatcher uses persisted claims, lease fencing, four concurrent deliveries per server process and at most three attempts. A restart retries the same message ID and link; uncertain SMTP delivery can result in a duplicate email, never a second authentication grant. Expired/discarded work and finished deliveries clear their encrypted message payloads. SMTP runs in a separate worker with a 64 MiB V8 old-generation limit and a twenty-second overall deadline. The controller kills the cgroup and confirms that no processes remain before returning an operation result or exporting the candidate. Failure to confirm termination closes the controller. A known agent/provider failure after edits retains an explicitly unverified candidate and diff; successful tasks still require independent checks in a fresh VM. Cloud workers also reject client execution profiles before claiming a task or preparing an environment.
