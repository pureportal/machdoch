# Approval review investigation

The shader-directory incident remains unattributed: its original command, tool response, executable, and effective permissions were not recovered. The current source does pass the full-access flag on ordinary Codex executions, but that does **not** establish that every policy check is disabled. Matching upstream Codex 0.159.1 code contains a command rejection path that is separate from automatic approval review.

Investigated on October 7, 2026 against working-tree sources based on `d63006fb127d78dcb97cd8a1a99468560d8f4bca`, including existing uncommitted changes. Only this report and the diagnostic probe script were added. No production behavior was changed, no development servers were started, and the rejected cleanup was not retried.

## Findings

### 1. A policy rejection is possible without automatic approval review

**Confirmed upstream mechanism; unverified cause of the shader incident.** The locally resolved CLI reports `codex-cli 0.159.1`. Its help describes the bypass flag as skipping confirmations and sandboxing. In the matching [upstream exec launcher](https://github.com/openai/codex/blob/rust-v0.159.1/codex-rs/exec/src/lib.rs#L328), the flag requests full access and preserves the headless `never` approval policy.

However, [exec_policy.rs:770](https://github.com/openai/codex/blob/rust-v0.159.1/codex-rs/core/src/exec_policy.rs#L770) forbids unmatched commands classified as dangerous under `Never`, independently of unrestricted filesystem access. Its rejection formatter emits `blocked by policy` for the `Other` classification. `--ignore-rules` skips user/project rule files, while other configuration layers and managed policy remain eligible. Windows classification explicitly covers `Remove-Item ... -Force`, including `-Recurse`: [windows_dangerous_commands.rs:501](https://github.com/openai/codex/blob/rust-v0.159.1/codex-rs/shell-command/src/command_safety/windows_dangerous_commands.rs#L501). [orchestrator.rs:196](https://github.com/openai/codex/blob/rust-v0.159.1/codex-rs/core/src/tools/orchestrator.rs#L196) returns forbidden decisions before command execution.

This gives a concrete explanation for that generic text even when the expected flag was present. It does not prove that this mechanism processed the shader command. Ordinary auto-review remains a separate mechanism: OpenAI's [auto-review documentation](https://learn.chatgpt.com/docs/sandboxing/auto-review) states that normal review requires an interactive approval policy.

**Targeted check:** recover the exact command/tool response and binary identity; evaluate the command through that version's parser/policy logic without executing the deletion. Check whether the response contains a heuristic rejection, a reviewer rationale, a managed rule, or a remote-tool error.

### 2. “Full access” does not describe every parallel or special worker

**Confirmed behavior, not a missing flag defect.** Every managed CLI worker passes `scopedWorkerToolDefinitions`, so even a write worker selects read-only Codex shell access. Worker tools are limited to claimed file operations; there is no directory-removal or shell tool in the write-worker set: [parallel-agent-sessions.ts:37](../apps/client/src/core/_helpers/parallel-agent-sessions.ts#L37), [parallel-agent-sessions.ts:316](../apps/client/src/core/_helpers/parallel-agent-sessions.ts#L316). A cleanup attempted with a native shell in that worker cannot inherit the parent's bypass branch.

The Codex scoped branch retains native shell availability, unlike internal inference, Claude scoped workers, and Copilot scoped workers. Machdoch path claims are enforced by the MCP wrappers, not by each provider-native read operation. A read-only shell sandbox is therefore not equivalent to the claimed-file boundary. Native Codex child permissions are also not observed by Machdoch.

**Unverified edge:** scoped/artifact launches do not explicitly set `approval_policy` or `approvals_reviewer`. Matching Codex [build_exec_config](https://github.com/openai/codex/blob/rust-v0.159.1/codex-rs/exec/src/lib.rs#L758) can honor an AutoReview configuration when the bypass flag is absent. Isolated user config alone does not establish the effective managed configuration.

**Targeted check:** identify whether the cleanup came from the parent, a managed worker, a provider-native child, or an evaluator. Capture each process/thread's requested and effective approval policy, reviewer, permission profile, sandbox backend, and enabled native tools. Use harmless reads to test claim enforcement; do not retry deletion to infer permissions.

### 3. Native command and MCP failures are discarded from ordinary final results

**Confirmed reporting defect.** [external-agent-cli-output.ts:293](../apps/client/src/core/_helpers/external-agent-cli-output.ts#L293) handles assistant messages and item diagnostics, but does not preserve command/MCP failure status as a run failure or separate ordinary-run evidence. A later `turn.completed` yields exit code 0. Tool evidence is captured only when requested and is bounded: [external-agent-cli-output.ts:114](../apps/client/src/core/_helpers/external-agent-cli-output.ts#L114). Ordinary tasks and managed workers do not enable that evidence option; goals do.

The launcher returns decoder output rather than raw stdout, streams only decoder display text, and uses the process/terminal result for task status: [external-agent-provider.ts:1035](../apps/client/src/core/_helpers/external-agent-provider.ts#L1035), [external-agent-provider.ts:1250](../apps/client/src/core/_helpers/external-agent-provider.ts#L1250), [external-agent-provider.ts:2596](../apps/client/src/core/_helpers/external-agent-provider.ts#L2596). Raw stderr can survive, but there is no guaranteed stored original tool response or unresolved-failure record.

Two diagnostic probes supplied a failed native command and failed MCP item followed by a completed turn. Both returned result exit code 0 and no failure message. Only the evidence-enabled decoder retained the failures. This does not mean every transient tool error should fail a task; the defect is the absence of evidence needed to distinguish a recovered error from unfinished cleanup.

**Targeted check:** retain structured tool failures independently of terminal success, with command/tool identity and recovery outcome. Test an unresolved rejection followed by a successful call and final answer, including native parallel child events.

### 4. A related rejection exists in retained logs, but it is not the shader incident

**Confirmed historical evidence.** [.machdoch/ralph/runs/2026-10-01T06-14-41-274Z/trace.jsonl:55](../.machdoch/ralph/runs/2026-10-01T06-14-41-274Z/trace.jsonl#L55) and line 56 contain raw `codex_core::tools::router` stderr reporting `exec_command failed`, `CreateProcess`, and `rejected: blocked by policy` for PowerShell temporary relocation-directory deletion with `-Force`. Line 57 is the agent's subsequent attribution to automatic approval review; the raw error itself does not identify a reviewer.

[execution-history.jsonl:11](../.machdoch/ralph/runs/2026-10-01T06-14-41-274Z/execution-history.jsonl#L11) records Codex 0.159.1, `access: full local access`, `execpolicy rules: ignored`, exit code 0, task status `executed`, and block status `completed`, despite retained cleanup failure. Those access labels describe Machdoch's requested launch behavior; they are not a provider-reported effective-settings snapshot.

The October 6/7 verification documents contain other cleanup-rejection narratives. They are not original shader tool responses. Searches of source, selected workspace logs, and Machdoch RALPH log directories did not recover the shader-specific response. Machdoch chat-history tools were not callable in this invocation.

**Targeted check:** correlate the shader wording to a run ID, timestamp, task/block, and tool call. Do not reuse the relocation-run attribution as proof of its cause.

### 5. Native goals neither validate effective permissions nor preserve approval-request details

**Confirmed defects, reproduced with protocol fixtures.** After requesting `never` and full access, [codex-native-goal.ts:117](../apps/client/src/core/_helpers/codex-native-goal.ts#L117) checks only `result.thread.id`. The provider's [ThreadStartResponse](https://github.com/openai/codex/blob/rust-v0.159.1/codex-rs/app-server-protocol/schema/typescript/v2/ThreadStartResponse.ts) exposes approval policy, reviewer, and sandbox information, but Machdoch does not compare or retain them. A probe returning `on-request` and a read-only sandbox still advanced to `thread/goal/set`.

[codex-native-goal.ts:163](../apps/client/src/core/_helpers/codex-native-goal.ts#L163) handles any server request as unsupported interaction. A synthetic command-approval request with a specific policy reason became `Codex requested user input. Resume after resolving it.` The method, command, and reason were lost. This can obscure an actual policy request; it does not establish one occurred in the reported run.

The app-server argv also lacks ordinary exec's `--ignore-rules`, and its launch metadata omits the requested access policy: [external-agent-provider.ts:1577](../apps/client/src/core/_helpers/external-agent-provider.ts#L1577). Its policy isolation is consequently not identical to ordinary exec.

**Targeted check:** validate the `thread/start` response before continuing; retain the actual server-request method and sanitized reason. Check app-server rule loading and native-child permission inheritance against the deployed CLI version.

### 6. Managed worker failure tracking works for scoped tools, but CLI answer reporting can contradict status

**Confirmed protections and a reporting defect.** Both CLI and API workers remember earlier scoped tool errors instead of resetting after later success: [parallel-agent-sessions.ts:418](../apps/client/src/core/_helpers/parallel-agent-sessions.ts#L418), [parallel-agent-sessions.ts:627](../apps/client/src/core/_helpers/parallel-agent-sessions.ts#L627). [local-mcp/runtime.ts:74](../apps/client/src/core/local-mcp/runtime.ts#L74) reports returned errors to the worker callback, including unknown-tool and argument-validation errors. Tests cover these cases. Write workers must also complete at least one scoped edit. Native Codex shell failures are outside these MCP callbacks and have the gap in finding 3.

When managed workers fail, the CLI parent branch changes `status`, `summary`, and `reason`, but leaves `response.markdown` unchanged: [agent-runtime.ts:2543](../apps/client/src/core/agent-runtime.ts#L2543). The API branch adds a failure notice to that markdown: [agent-runtime.ts:2597](../apps/client/src/core/agent-runtime.ts#L2597). A consumer displaying the CLI answer can therefore show success-oriented text alongside a failed status.

**Targeted check:** test the parent result and rendered answer after a failed worker and a success-oriented parent answer. Keep worker/tool identity and unresolved cleanup visible in the result consumed by the UI.

### 7. Machdoch shell cleanup has its own Windows error-reporting gap

**Confirmed defect; no evidence it produced the policy message.** Machdoch's `run_shell_command` runs a PowerShell subprocess through Node, not through Codex's native exec policy: [shell-network-tool-definitions.ts:214](../apps/client/src/core/_helpers/shell-network-tool-definitions.ts#L214). Its bootstrap does not set terminating-error behavior: [shell-network-tool-definitions.ts:26](../apps/client/src/core/_helpers/shell-network-tool-definitions.ts#L26). Success depends on the process exit code; stderr alone does not mark an error.

A harmless probe executed `Write-Error` followed by `Write-Output`. The actual tool returned exit code 0, no `isError`, and error text in stderr. A failing cleanup followed by a successful statement can similarly be misreported. No deletion was performed in this probe.

Machdoch's host-side cleanup is another distinct boundary: enrollment disposal calls Node `rm`, with filesystem error codes and deferred-cleanup metadata ([materializer.ts:232](../apps/client/src/core/provider-enrollment/materializer.ts#L232)); image cleanup calls Rust `remove_dir_all`. RALPH deterministic command blocks call `executeLocalCommand` directly ([ralph.ts:5853](../apps/client/src/core/ralph.ts#L5853)). These operations do not acquire Codex permissions merely because an agent requested them.

No shader-specific cleanup routine or special shader permission path was found in the searched application and build scripts. The original directory and cleanup command remain unknown.

**Targeted check:** identify the actual cleanup implementation; preserve its OS error and verify the directory's postcondition before claiming removal. Test a nonterminating PowerShell failure followed by successful output.

### 8. Existing diagnostics record intent more reliably than effective policy

**Confirmed observability gap; several plausible causes remain unverified.** The assembled request digest includes final argv but does not make those arguments recoverable: [external-agent-provider.ts:2065](../apps/client/src/core/_helpers/external-agent-provider.ts#L2065). The enrollment manifest records enrollment arguments, not the complete command, and is disposed after the run: [materializer.ts:1095](../apps/client/src/core/provider-enrollment/materializer.ts#L1095). Launch progress records requested access, while final instruction metadata does not retain a provider-confirmed permission snapshot. Native children are not individually instrumented.

The capability probe checks Codex config/JSON delivery features, not every emitted isolation/access flag: [capability-registry.ts:169](../apps/client/src/core/provider-enrollment/capability-registry.ts#L169). An unsupported flag normally causes launch failure, not a silent policy downgrade; there is no evidence of a permission retry that removes the flag. A configured wrapper, another installed binary, stale embedded/bundled Machdoch code, managed requirements, a provider-native child, or an external MCP policy could explain a mismatch, but none has been demonstrated for the shader run.

Source searches found no Machdoch cleanup error generator containing `Automatic approval review`. The only source occurrence of `blocked by policy` is an unrelated Google voice-response test fixture: [google_response.rs:356](../apps/client/src-tauri/src/voice/google_response.rs#L356). Machdoch's own Ask-mode denial has different wording: [agent-tools.ts:67](../apps/client/src/core/_helpers/agent-tools.ts#L67). MCP error results are passed back with their error indication: [local-mcp/server.ts:25](../apps/client/src/core/local-mcp/server.ts#L25). Thus the phrase alone cannot identify the rejecting component.

**Targeted check:** collect a sanitized launch record containing executable path/version/hash, deployed Machdoch bundle identity, final argv, execution role, parallel mode, and per-process/thread permission settings. Preserve the original tool response and distinguish `provider-policy`, `reviewer-denial`, `Machdoch-mode`, `remote-tool`, and `filesystem` origins from agent-written summaries.

## Verification and limits

The focused existing suite passed **200 tests across 8 files**: external-agent launcher/decoder, managed CLI/API workers, native goals, enrollment materialization, local MCP server, and shell tools. These include mocked launches; they do not verify the shader run's effective settings.

Run the five non-destructive probes with:

```powershell
pnpm exec oxnode docs/validation/approval-review/probes.ts
```

All five reproduced the stated behavior on this Windows workspace. The probe fixtures and PowerShell error are synthetic. Matching upstream source was inspected, not built or executed. No live agent policy denial, native child launch, packaged desktop deployment, or original shader cleanup was reproduced. The decisive missing evidence remains the shader run's original tool response and effective settings.
